# ADR-013：用户任务连续性与内部执行分段

## 状态

- 状态：Accepted
- 日期：2026-07-19
- 决策者：Maintainer
- 实施入口：`CTX-SEG-01`
- 取代：阶段性 Session Handoff 的普通用户显式创建与确认流程

## 背景

Zebra 已经具备耐久 Session lineage、不可变 Handoff Envelope、原子子 Session
创建、Effect Ledger、authority narrowing、Workspace revision、outbox 和恢复合同。
这些合同解决了跨执行边界的连续性与安全问题，但最初产品实现把内部执行边界
直接暴露成 Desktop 的“阶段性新线程”表单，要求用户填写下一阶段标题、目标和
首条指令，并预览 Envelope 后确认创建 child Session。

这混淆了两个不同概念：

- Task 是用户委托给 Zebra 的稳定工作单元；
- Session/Segment 是 Runtime 为完成 Task 使用的内部执行载体。

上下文容量、Provider continuation、Worker 恢复和执行阶段划分属于 Agent Runtime
职责。用户只应在权限扩大、高风险副作用、澄清和业务决策时被打断，不应承担
内部上下文治理。

## 决策

### 1. 一个用户任务只有一个稳定产品身份

Zebra 将引入稳定 `task_id` 作为用户、外部业务系统和普通 Desktop 的主标识。
侧边栏条目、URL、消息追加、停止、恢复、续问、审批和流式游标都绑定 Task，
不得因内部执行分段变化而改变。

### 2. Session Handoff 降级为内部 Execution Segment Rollover

现有 handoff 安全合同继续保留并复用，但不再表示用户主动创建新线程。每个
Task 可以拥有一个或多个内部 Execution Segment；Runtime 在安全边界原子关闭
当前 Segment、生成透明 Checkpoint/Envelope，并激活唯一后继 Segment。

内部 Segment ID、handoff ID、stage index、Envelope、首条阶段指令和 lineage
默认不进入普通用户 API、侧边栏或聊天时间线。它们只在受控 operator/audit
接口中可检查。

### 3. 生命周期控制由后端决定

新增确定性的 `ContextLifecycleController`。它综合以下事实决定继续、压缩或
rollover：

- Context Window Planner 的 soft/hard watermarks；
- Context Capsule 数量、压缩收益和恢复质量；
- Provider continuation 可用性与协议边界；
- Worker/Runtime 恢复要求；
- 已验证计划阶段或 Agent 发出的 typed rollover hint。

Agent hint 不是权限，也不能直接创建 Segment。Controller 必须重新检查安全边界、
lease、pending tool/approval/clarification、Effect Ledger、Workspace revision 和
authority。普通 context pressure 优先在当前 Segment 自动 compaction；只有继续
当前 Segment 已无收益或恢复需要新载体时才 rollover。

### 4. 自动切换不得扩大权限或隐藏真实用户决策

Segment rollover 只能保持或收窄 Policy、Tool、Network、MCP、Credential 和
Workspace authority。存在未决审批、澄清、运行中工具、未知外部副作用或权限
扩大请求时必须停止 rollover，并走现有用户审批/澄清流程。

自动化只隐藏实现机制，不隐藏风险、失败、费用、审批、澄清和用户可行动状态。

### 5. Task 拥有统一投影与流

Task Projection 聚合所有内部 Segment 的用户消息、Assistant 输出、工具摘要、
审批、澄清、Artifact、状态和 usage。Task Event Stream 使用独立单调 sequence；
Segment 切换不得重置 SSE cursor、重复消息或要求前端跳转。

普通 Session 列表必须排除 `visibility=internal` 的 Segment。停止、恢复、续问和
审批命令由 Task Coordinator 路由到当前 `active_segment_id`。

## 用户体验不变量

普通用户界面不得出现：

- 阶段性新线程或 Start next stage；
- 下一阶段标题、Objective 或 Stage Prompt；
- Preview Envelope、known omissions 或 checksum；
- child Session、handoff ID、stage index 或 lineage breadcrumb；
- 因内部 rollover 产生的新侧边栏会话或页面跳转。

必要时 UI 只能显示非交互状态“正在整理上下文并继续执行”，且不得要求用户参与。

## 保留的安全不变量

- Event Store 仍是事实源，Envelope/Checkpoint 可验证且不可变；
- 同一 Task 只有一个活动写入 Segment；
- rollover 使用 CAS/fencing/idempotency/outbox，崩溃恢复不得创建第二后继；
- effectful tool 的 terminal ledger 跨全部 Segment 生效，禁止静默重放；
- provider-private reasoning、continuation、Credential 和原始大输出不跨 Segment；
- Workspace drift、Snapshot 篡改和 authority drift 均 fail closed。

## 迁移和兼容

1. P0 立即移除普通 Desktop handoff 创建入口；后端合同保持默认关闭。
2. P1 引入 Task/Segment 领域合同与 Task Projection，不改变现有 Session 数据。
3. P2 引入 Task API、Task SSE 和 Coordinator 路由，Desktop 切换到 Task identity。
4. P3 引入自动 Lifecycle Controller，并将现有 handoff mutation 收入 internal API。
5. P4 为已有 lineage 回填 Task，隐藏内部 child Session，保留 operator 审计。
6. 兼容期后废弃普通公开 handoff create/preview 和 CLI 用户命令。

## 被否决方案

### 仅用 feature flag 隐藏卡片

否决。它仍保留错误产品合同，且前端/后端 capability 漂移会再次暴露入口。

### 删除所有 handoff 后端能力

否决。原子 lineage、no-replay、authority 和 crash recovery 是内部分段需要的安全
基础，重写会增加风险。

### 每次上下文压力都自动创建 child Session

否决。同一 Segment compaction 仍是首选；无条件切换会增加存储、恢复和调度成本。

### 继续让用户确认内部阶段

否决。确认应服务于权限与副作用边界，而不是 Runtime 的上下文实现。

## 验收

- 普通用户完成简单任务后看不到任何 handoff 控件；
- 长任务跨 Segment 后仍只有一个 Task、一个 URL 和连续 SSE cursor；
- 停止、恢复、续问、审批和澄清跨 Segment 正常工作；
- 并发、崩溃、漂移、篡改、未知副作用和 no-replay 矩阵保持 fail closed；
- operator 可审计完整 lineage，但普通 API/UI 不泄漏内部 Segment 实现。
