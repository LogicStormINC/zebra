# Zebra Agent 主线架构工程完成度审计与收口计划 v1.0

## 1. 文档目的

本文记录 Zebra Agent 当前 `main` 的真实完成度、验证证据、主要缺口和后续收口顺序。
它解决三个长期问题：

1. 不再用递增的内部 Phase 编号代替产品完成度。
2. 严格区分已经合入主线的能力、仅存在于本地分支的改动和仍处于规划中的能力。
3. 为下一轮工作提供有依赖、所有者、Owned paths 和验收标准的任务入口。

本文是阶段判断和收口计划，不替代最终架构文档、任务注册表或逐任务验收记录。

## 4. 完成度口径

完成度使用两个不同目标，不能合并成一个模糊数字：

### 4.1 本地产品目标

“本地产品”指单机运行、持久会话、可恢复 Harness、受控工具、Policy/HITL、API/CLI/Worker
和 Desktop 能组成可实际使用的工程 Agent。

结论：**80%–85%，属于功能完整的本地 Beta。**

### 4.2 最终平台目标

“最终平台”按最终架构中的团队协作、强隔离 Runtime、ACP、私有云、多租户、远程凭证、
生产 Egress、远程 Sandbox 和生态能力计算。

结论：**55%–65%，尚未达到生产级平台。**

这些区间不是按内部 Phase 数量计算，而是根据架构能力是否实现、是否进入主线、是否通过门禁、
是否具备生产隔离和是否具备持续交付能力综合判断。

## 6. 已经完成且应保持的架构基础

1. `agent-core` 保持基础设施无关，其他 package 通过 Ports 与其协作。
2. Session Event Store 是持久事实来源，恢复依赖事件与投影而不是前端内存。
3. Harness 和 Worker 已经形成可停止、可恢复、可验证的本地执行闭环。
4. 工具经过 Typed Contract、Policy、HITL、事件和审计路径，不把模型输出直接当作权限。
5. Workspace、Artifact、Memory、Snapshot 和 Git 各有独立职责。
6. API、CLI、Worker 和 Desktop 复用持久状态，而不是维护互相冲突的产品状态机。
7. 文件大小、类型检查、测试和 Eval 已经形成明确的本地质量门禁。

后续收口不得通过把业务逻辑重新塞回 `apps/`、绕开 Policy、暴露自由 Shell、使用前端临时状态
替代持久事件或弱化现有测试门禁来换取速度。

## 7. 当前问题清单

### P1：主线缺少已经验证的桌面修复

以下本地提交尚未进入本次审计的 `main`：

- `d0b0c41 fix(ui): enable unbound session continuation`
- `3c2948f feat(ui): add truthful agent runtime feedback`

影响：主线仍可能出现历史未绑定会话无法续问、运行反馈不真实或交互语义冲突。

要求：通过一个依赖清晰的 UI PR 合入，不手工复制差异；合入前重跑桌面检查、生产构建和真实浏览器回归。

### P1：缺少自动化 CI

主线没有 `.github/workflows`。当前门禁可靠，但依赖开发者主动执行。

影响：PR 可以在没有自动测试、类型检查、文件大小门禁、Eval 或前端构建证据的情况下被合并。

要求：新增最小 CI，只运行已有命令，不引入新的构建系统或重复脚本。

### P1：生产 Runtime 的能力声明尚未决策

`ARCH-129-RT-01`、`ARCH-129-ACP-01`、`ARCH-129-CTX-01` 仍为 `Locked`。

影响：本地 Beta 可以继续，但不能把当前 Local Runtime 宣称为生产级强隔离 Sandbox，也不能宣称已支持 ACP 或代码智能。

要求：由维护者明确选择“继续保持本地 Beta”或“激活 Hard Runtime”。在此之前不得隐式启动这些任务。

### P2：任务注册表状态与 Git 历史不一致

`QA-2-STO-01`、`QA-39-MEM-01`、`QA-2-ARCH-01` 的实现和合并提交已经进入主线，任务卡仍为 `Review`。

影响：任务统计显示 `450 Done / 3 Review / 3 Locked`，不能准确表达真实主线状态。

要求：核对对应 merge commit 后将三个任务改为 `Done`，不得仅依据分支存在性修改状态。

### P2：长期文档已经漂移

- `PROGRESS.md` 声明 Phase 145 完成。
- `README.md` 的 Current Status 仍以 Phase 101 开头，并包含难以维护的超长能力段落。
- `docs/实施任务拆解与阶段验收.md` 仍把 Phase 1–3 写成“本周建议顺序”。

影响：新贡献者无法从入口文档判断当前主线、下一阶段或能力边界。

要求：README 只保留稳定产品能力和入口；PROGRESS 负责当前状态；实施文档保留原始阶段基线并明确其历史性质。

### P2：桌面端包体持续超出建议阈值

生产构建主 chunk 约 `1.33 MB`，Vite 持续给出大 chunk 警告。

影响：桌面 WebView 首次加载、调试刷新和低性能设备体验会随功能增长继续恶化。

要求：先生成可重复 bundle 报告，再按路由或重依赖边界拆分；不得用提高 warning limit 掩盖问题。

### P3：最终平台路线没有新的激活决策

私有云、多租户、远程凭证代理、生产 Egress、远程 Sandbox、Kubernetes 和生态能力仍主要在最终架构文档中。

影响：这不是当前本地 Beta 的缺陷，但如果产品目标已经转向团队或云平台，需要重新排序资源。

要求：在 Hard Runtime 决策之后再制定平台阶段，不从 UI 或单个 API 入口倒推云架构。

## 12. 明确非目标

本审计不授权以下工作：

- 自动合并任何分支
- 直接修改 `main`
- 自动解锁 `ARCH-129` 实现任务
- 引入 Kubernetes、远程 Sandbox、远程 MCP、OAuth 或多租户控制面
- 绕过现有 Policy、HITL、网络、凭证、事件或测试边界
- 以 Phase 编号、提交数量或测试数量单独推导产品完成百分比

## 13. 维护规则

- 每次主线能力边界变化后更新审计基线提交和相关分层判断，不滚动重写历史证据。
- `PROGRESS.md` 记录当前主线状态；README 只记录稳定入口和产品能力；任务状态只在满足合并条件后变更。
- 新的生产平台能力必须先形成任务卡、依赖、Owned paths、威胁边界和验收标准。
- 如果本地 Beta 与最终平台目标发生变化，先更新本文件的完成度口径，再调整后续任务顺序。
