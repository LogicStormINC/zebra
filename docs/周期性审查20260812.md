# 结论

我查看的是当前公开仓库 `LogicStormINC/zebra` 的 `zebra-cloud-trench` 分支。截至 **2026 年 8 月 12 日**，GitHub 显示该分支共有 848 个提交，最新提交为 **2026 年 8 月 5 日的 `978e02d`**，主要完成 durable AG-UI projection contract 的收尾。([GitHub][1])

按三个不同口径评估：

| 评估口径                             |        当前完成度 |          剩余距离 |
| ------------------------------------ | ----------------: | ----------------: |
| 已经写出的 Cloud 代码资产            |     约 65% 至 70% |     约 30% 至 35% |
| 可实际交付的完整 Cloud Agent 闭环    | **约 45% 至 50%** | **约 50% 至 55%** |
| 多租户、可扩缩容、生产级 Cloud Agent |     约 35% 至 40% |     约 60% 至 65% |

**我的核心判断是：Zebra 已经完成了相当多的云端持久化与一致性底座，但距离能够稳定启动、处理真实代码仓库、执行副作用工具、接入 Trench 并长期运行的完整 Cloud Agent，仍有大约一半距离。**

剩余部分看起来代码量未必特别大，系统集成风险很高。主要工作已经从“实现更多 Store”转向“把 Store、Worker、Runtime、Workspace、Authority、Streaming 组合成一条真实运行链路”。

# 一、旧审查结论已经明显过期

当前 README 仍写着 cloud runtime composition 继续选择 SQLite，并声称 Zebra application image 尚未实现。但源码已经包含：

1. `cloud` profile 的 PostgreSQL composition。
2. S3 Artifact Object Store。
3. PostgreSQL Effect Outbox。
4. PostgreSQL Lease Fence。
5. API、Worker、Migration 三类 Docker image。
6. `compose.application.yml` 中独立的 API 和 Worker 服务。
7. PostgreSQL backup、fresh restore、fenced recovery drill。
8. AG-UI durable projection contract。

这说明代码已经从早期的“云架构文档阶段”进入了“云底座基本完成、运行组合尚未闭合”的阶段。README 当前确实落后于源码。([GitHub][1])

# 二、已经完成得比较好的部分

## 1. PostgreSQL Control Plane 完成度较高

`postgres_control_plane_stores()` 已经组合了：

```text
Event Store

Workspace Projection
Agent Task
Lease
Context Lifecycle
Context Materialization
Session Handoff
Handoff Dispatch
Idempotency
Effect Dispatch
Governed Memory
Artifact Payload
Model/Tool Projection
Session Artifact
Provider Continuation
Session History
Delivery Audit
```

这已经超过普通 Agent 项目的存储层成熟度。尤其是 Event、Projection、Lease、Effect、Continuation、Artifact 之间开始形成统一的 namespace-bound cloud bundle。

## 2. Lease、Fencing 和 Effect Outbox 设计成熟

Worker 已经有持续 Lease Heartbeat，执行期间会检查 ownership。PostgreSQL Effect Dispatch 在 schedule 和 claim 时验证当前 Lease Fence，并通过事务保存 Effect intent、delivery state 和 terminal event。Effect claim 使用数据库锁定机制控制多 Worker 并发。

这部分已经具备生产级 Agent 最核心的一致性思想：

```text
旧 Worker 失去 Lease
→ 旧 Fence 失效
→ 后续持久化和副作用调度被数据库拒绝
```

相关恢复提交还覆盖了 logical backup、fresh restore 和 fenced recovery drill。

## 3. Agent 执行核心已经较完整

当前 Worker 执行路径已经包含：

```text
Lease Acquire
→ Heartbeat
→ Session Recovery
→ Workspace Restore
→ Handoff Recovery
→ Context Capsule
→ Provider Continuation
→ Runtime Provision
→ Tool Gateway
→ Effect Guard
→ Harness Execution
→ Approval / Clarification Continuation
→ Event / Projection Commit
→ Memory Extraction
→ Finalization
```

从 Agent Runtime 自身能力看，Zebra 已经是一个较成熟的 local-first engineering agent。Agent loop、上下文压缩、恢复、工具执行、审批、澄清、Artifact 和 Memory 都有实际代码支撑。

## 4. Runtime Adapter 基础合理

Runtime 已支持：

```text
trusted-local
os-sandbox
oci-rootless
gvisor
```

OCI Runtime 会检查运行时能力、绑定 Workspace、关闭网络、只读根文件系统、移除 capability、限制 CPU、内存、PID 和 tmpfs。方向正确，后续无需重写 Runtime 抽象。

# 三、当前最严重的三个 P0 问题

## P0.1 默认 Cloud Worker 的 Effect Dispatch 没有真正接通

这是本次源码审查中最严重的问题。

Cloud Store 的契约中：

```python
effects: EffectDispatchPort
```

Local Store 的契约中：

```python
effects: EffectLedgerPort
```

Cloud composition 最后使用：

```python
cast(ControlPlaneStores, stores)
```

把 `PostgresControlPlaneStores` 强制转换成 local `ControlPlaneStores` 类型。这个 cast 隐藏了两个 `effects` 接口的实际差异。

默认 Worker 启动链路是：

```text
worker main
→ build_worker_loop_service()
→ effect_dispatch=None
→ SessionExecutionService
→ _effect_ledger = active_stores.effects
→ guard_effectful_tools(dispatch=None)
→ EffectGuardedToolGateway
→ ledger.reserve(...)
```

然而 cloud profile 下的 `active_stores.effects` 实际对象是 `PostgresEffectDispatchStore`，它实现的是：

```text
schedule
claim_next
complete
resolve_uncertain
retry
dead_letter
```

Legacy gateway 期待的是：

```text
reserve
mark_executing
mark_succeeded
mark_uncertain
```

默认 Worker main 没有传入 `effect_dispatch`，Worker loop 也没有自动使用 `active_stores.effects` 作为 fenced dispatch。

因此，按照当前默认 cloud composition 静态推断：

1. 纯读工具大概率可以执行。
2. 第一个产生副作用的工具调用，极可能发生接口方法缺失。
3. Cloud Effect Outbox 已经实现，但默认 Worker 没有走进去。
4. Cloud Artifact Effect Payload 和 mutation authority 也无法正常进入完整路径。

这个问题会直接阻断文件修改、命令执行、Git 提交、PR、外部写操作等核心能力。

### 应有的组合方式

Cloud Worker composition 应显式注入：

```python
effect_dispatch=cloud_stores.effects
worker_projection_transaction=cloud_stores.workspaces
cloud_artifact_factory=...
cloud_provider_continuation_factory=...
execution_authority_resolver=...
execution_authority_scope=...
```

同时应删除通过 `cast(ControlPlaneStores, stores)` 兼容两个不等价 Effect Port 的做法。更稳妥的方案是建立统一的 application-facing store bundle，或者把 local 和 cloud effect execution 分成明确的 strategy。

## P0.2 `cloud` 与 `production` Profile 语义发生分裂

当前存储选择逻辑是：

```text
profile == cloud
→ PostgreSQL + S3

其他 profile
→ SQLite
```

Runtime 选择逻辑是：

```text
profile == production
→ 默认 gVisor
→ 强制 Workspace quota
→ 强制镜像 digest

其他 profile
→ 默认 trusted-local
```

`compose.application.yml` 设置的是：

```text
ZEBRA_PROFILE=cloud
```

同时没有设置 `ZEBRA_RUNTIME_CLASS`、`ZEBRA_RUNTIME_IMAGE` 和 Workspace quota。由此得到的默认组合是：

```text
PostgreSQL + S3
+ trusted-local Runtime
```

`trusted-local` 最终通过 Worker 容器内的 host subprocess 执行命令。

反过来设置：

```text
ZEBRA_PROFILE=production
```

会触发 gVisor fail-close，但存储 composition 会走 SQLite。

手动给 cloud profile 补充 gVisor 环境变量可以绕过部分问题，但 profile 本身没有提供生产安全门禁。标准配置模型目前无法完整表达：

```text
cloud deployment
+ PostgreSQL
+ S3
+ Redis
+ gVisor
+ Workspace quota
+ mandatory auth
+ fail-close
```

### 推荐调整

将单一 `profile` 拆成正交配置：

```text
deployment_mode:
  local
  single_host
  cloud

security_mode:
  development
  hardened
  production

storage_backend:
  sqlite
  postgres

runtime_backend:
  trusted_local
  os_sandbox
  oci_rootless
  gvisor
```

然后增加一个 `cloud-production` validation policy：

```text
PostgreSQL 必需
S3 必需
Redis 必需
gVisor 必需
Workspace Provider 必需
API Auth 必需
Authority Resolver 必需
Effect Dispatch 必需
```

缺少其中任何一项时，进程启动失败。

## P0.3 没有真正的 Cloud Workspace Control Plane

API 创建 Session 时直接执行：

```python
Path(workspace).expanduser().resolve()
```

然后把本地绝对路径写入 Task 和 Workspace Projection。Worker 随后拿这个路径创建 Runtime。

默认 Docker Compose 中：

1. API 和 Worker 是两个独立容器。
2. 两者没有共享 Workspace volume。
3. Worker 没有 Docker socket。
4. Worker 没有 remote runtime endpoint。
5. 没有 Git clone 或 checkout 服务。
6. 没有 Workspace volume provisioner。
7. 没有初始 Workspace snapshot materialization。
8. 没有 Workspace 回收和 quota controller。([GitHub][2])

因此，API 容器中解析出来的：

```text
/workspaces/repo-a
```

在 Worker 容器中通常不存在。即使存在，gVisor 或 OCI Runtime 还需要 Worker 能访问 Docker 或 Podman Engine，并把该路径 bind mount 到 Sandbox。

当前默认 Compose 更接近：

```text
Cloud Control Plane Demo
```

还没有形成：

```text
Cloud Coding Agent Runtime
```

### Workspace Control Plane 至少需要

```text
WorkspaceSource
  git repository
  uploaded archive
  existing durable snapshot
  Trench project reference

WorkspaceInstance
  workspace_id
  source_revision
  volume_ref
  owner namespace
  active attempt
  writable lease
  quota
  lifecycle state

Workspace lifecycle
  provision
  clone / materialize
  seal
  snapshot
  restore
  handoff
  release
  garbage collect
```

这一部分是完整 Cloud Agent 与本地 Agent 最大的基础设施差异。

# 四、另外四个重要缺口

## 1. Cloud API 仍然绕过 Worker

`create_session()` 支持 `execute=true`，此时 API 直接调用 `run_local_harness()`。`resume_session()` 也会在 API 进程内直接构造 `SessionExecutionService`。

这会带来几个问题：

1. API 请求生命周期与 Agent 执行生命周期耦合。
2. API 无法独立扩容和快速返回。
3. 模型调用和工具执行占用 API Worker。
4. Cloud Worker 的 fencing、dispatch、artifact coordinator 和 authority resolver 被绕过。
5. API 重启可能中断正在执行的任务。
6. 无法形成统一的背压和公平调度。

Cloud profile 下 API 应只执行：

```text
验证请求
→ 验证 Authority
→ 原子创建 Task / Session / Workspace
→ 写入 Durable Command
→ 返回 task_id 和 cursor
```

模型和工具执行应全部进入独立 Worker。

## 2. API Aggregate 写入仍有事务缺口

创建 queued session 当前依次执行：

```text
append event 1
append event 2
...
save session
save workspace
```

追加用户消息也是：

```text
store attachment
append event
save session projection
```

其中任意一步发生进程退出，都可能留下：

```text
Event 已写，Projection 未写
Attachment 已写，Event 未写
Session 已写，Workspace 未写
```

PostgreSQL 层已经具备不少事务型 mutation adapter，但 API 入口还没有全面使用 aggregate transaction。

## 3. Host Authority 和多租户隔离还没有贯穿 HTTP 到 Worker

最新提交已经加入 generic host authority contracts，这说明领域契约方向已经形成。默认 HTTP 层目前仍采用：

```text
可选的单一静态 Bearer Token
```

当 token 未配置时，除 `/health` 外的请求直接放行。CORS 也允许任意 origin。Compose 默认允许 `ZEBRA_API_AUTH_TOKEN` 为空。Compose 将端口绑定到 loopback，降低了直接暴露风险，但服务间身份、请求级 Authority、subject、tenant、scope 和 limits 仍未接入默认路径。

`SessionExecutionService` 已经接受 `execution_authority_resolver`，默认 Worker main 和 Worker loop却没有注入它。因此 Host Authority 目前主要停留在 contract 和局部 adapter 层。

## 4. Redis 与 AG-UI 具备 Adapter，尚未形成默认运行链路

Redis Streams 的 `RedisLiveEventFanout` 已经实现 capture barrier、publish 和 read，并明确设计成 PostgreSQL replay 后接 Redis live tail。AG-UI 目录也已经具备 contracts、interrupts 和 projection。([GitHub][3])

当前 HTTP SSE 仍然每 50 毫秒轮询一次持久 Store，然后输出 Zebra 原生 `session_event` 或 `task_event`。API 中没有接入 Redis fanout，也没有暴露完整 AG-UI Runtime endpoint。

因此当前状态大致是：

```text
AG-UI domain projection: 已完成
Redis live adapter: 已完成
API live composition: 未完成
Trench BFF integration: 未完成
CopilotKit reconnect E2E: 未完成
```

Revision fencing
Attempt workspace
Snapshot / restore
Quota
Cleanup

全部 mutation 使用 PostgreSQL aggregate transaction。API 中的 `run_local_harness()` 和直接 `SessionExecutionService` 路径在 cloud profile 下应关闭。

并把 Authority 传入 Task、Session、Worker Attempt、Tool Effect 和 Artifact。

# 七、优先级建议

下一阶段不要先扩展更多 Store，也不应优先继续堆 AG-UI 事件类型。

优先顺序应固定为：

```text
1. 修复 Effect Dispatch 默认接线
2. 统一 cloud-production profile
3. 实现 Workspace Control Plane 最小版本
4. Cloud API 全部改成 command-only
5. 接通 Host Authority
6. 接通 Redis 与 AG-UI
7. 完成 Trench E2E
8. 补生产运维与混沌测试
```

前三项完成后，Zebra 可以达到“单机 Cloud Agent MVP”，能够开始真实 Trench 联调。

前六项完成后，可以称为“功能完整的 Cloud Agent”。

全部完成并通过恢复、隔离、滚动升级和负载门禁后，才能进入“生产级多租户 Cloud Agent”。

# 最终判断

当前 Zebra 已经越过了最早期架构验证阶段，也已经越过单纯 PostgreSQL Adapter 堆积阶段。

它目前处于：

```text
Agent 核心成熟
+ Cloud Control Plane 较完整
+ 分布式一致性设计先进
+ 默认运行组合未闭合
+ Workspace 基础设施缺失
+ Trench 产品链路未接通
```

所以我给出的最终数字是：

> **距离功能完整的 Cloud Agent 还有约 50% 至 55%。**

> **距离可用于 Trench 的单机 Cloud MVP 还有约 30% 至 35%。**

> **距离生产级、多租户、可横向扩容的 Cloud Agent 还有约 60% 至 65%。**

本次判断基于当前分支 HEAD 的静态源码路径审查，没有重跑完整 PostgreSQL、S3、Redis、Docker、gVisor 集成测试。Effect Port 错配、profile 分裂、Workspace 不可达和 API inline execution 均有直接源码证据，整体结论置信度较高。
