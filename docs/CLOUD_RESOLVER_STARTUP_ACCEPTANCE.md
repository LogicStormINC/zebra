# RESOLVER-STARTUP-01：有界 DNS 子进程启动优化

## 问题与最小改动

真实搜索验收在模型前失败：扩展列表 Host 准入约 2036ms 返回 503，原有 2 秒预算内
数据库连接耗时 1331ms，其中解析 1184ms；registry 查询约 54ms，JWKS 拉取约 583ms。
Worker 同时出现 TaskIO/DNS 超时重启。`/health` 的 HTTP 200 不能代替真实准入验收。

对解析子进程分段实测，JSON 模块加载约 310ms，实际 DNS 约 47ms。只去掉 JSON
或完整 socket 包装层，原生配对未证实稳定收益，因此没有把它们作为已验收成果。
进一步定位到字符串主机名触发 IDNA codec 及依赖加载。最终仅优化显式单一 ASCII
主机名和数字端口：用 `python -S` 启动可终止子进程，直接调用 CPython `_socket`
的原生 `getaddrinfo`，传等价 ASCII bytes，仅按原顺序返回地址。父进程保留完整 DSN、
TLS host、密码和其他参数，不把凭据放进命令行。未增加依赖、连接池或权限缓存。

国际化域名、service、多个主机、缺少显式端口、环境提供 host、prefer-standby、
random 选择均交回原 libpq 路径。30 秒地址缓存、环境失效规则、失败清缓存、每次新鲜
认证连接、原 2 秒预算、超时 kill/reap、COMMIT/SQL 处理与所有 Host 权限校验不变。

## 无模型证据

同一真实容器、同一 DNS 主机/端口，20 组交替 AB/BA，每次创建新的解析器，强制冷解析。
完全相同的地址及顺序逐次比对；仅进行解析，没有模型调用：

| 指标 | 原实现 | 最终实现 |
| --- | ---: | ---: |
| 成功 / 超时 | 20 / 0 | 20 / 0 |
| 墙钟中位数 | 979.703ms | 112.088ms |
| 子进程 CPU 中位数 | 687.171ms | 72.845ms |

本机资源竞争明显，绝对时间不作 SLA；墙钟下降约 88.6%，子进程 CPU 下降约 89.4%。
这些比例只针对冷解析，不等于页面首正文收益。未通过延长缓存、预算或放松校验获得。
在真实数据库上只读验证：原累积 2 秒预算内创建两次独立连接（不同 backend PID）、
各执行一次 SELECT，均关闭，总耗时约 392.5ms，未复用数据库连接或修改业务数据。
