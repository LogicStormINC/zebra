# Coverage 增量证明前置条件

日期：2026-10-10。状态：用户已批准增量提交、最终认证把关；实施中，尚未启用。

## 问题

原性能方案要求同时移除每次提交的历史物理重读，并完全保持现有拒绝语义。
代码审查确认，这两个目标在当前对象存储契约下不能直接同时满足。

反例：A 的模型原始响应已经结算；随后 A 的对象被删除或损坏，而数据库事件、
元数据与 witness 都未变化；此时提交另一条 B。当前完整验证拒绝该提交。
如果只检查 SQL 原始事件一致性和 B 的对象，提交会成功。最终认证再发现 A
损坏虽能防止正式发布，却改变了提交时拒绝的既有保证。

`indexed_state`、哈希、版本号或 verified 标志都不能证明物理对象仍存在。
因此不能将上述替换描述为“不降低校验强度”的实现。

## 当前实施决定

- 旧任务保留历史物理证明；新任务须在准入时显式绑定
  `validation_mode=final_certification`，允许当前单元及依赖的增量提交。
- 最终认证仍独立验证完整历史物理证据、生命周期、预算；失败不发布正式答案。
- 合并同一次读取中重复的前后权限/元数据检查，保留真实前后边界。
- 只在一次证明调用内复用不可变对象字节与已验证的回放结果。
- 不缓存撤权、STOP、租约或到期判定，不跨提交/回调复用授权。
- 复用达到内存限额后退回物理 I/O；新证明实例重新读取。
- “历史 A 损坏后提交 B”保留旧模式拒绝回归；新模式允许增量提交，
  但必须验证最终认证拒绝、没有正式报告发布。

## 真正增量协议的两种不同契约

1. 保持现有提交拒绝语义：先提供可信的不可变、保留锁定证据根。需要精确对象
   版本的不可变性、删除保护、完整性保证及可验证的保留期限；数据库源也需要
   完整性和原子扩展约束。必须证明该保证覆盖当前故障模型，而不是仅开启 S3
   versioning。存储端无法证明这些条件时不允许进入快速路径。
2. 改变接受契约：允许提交当前单元时只验证该单元及依赖，将不相关历史对象的
   损坏检查延迟到独立最终认证。这是产品语义变化，应明确授权、版本化并更新
   故障验收，不能静默切换。正式发布仍必须失败关闭。

用户已明确选用第二种。模式纳入原始准入、预算策略及摘要，不能在执行中切换，
旧 Worker 不得静默忽略；旧任务保持 eager 行为和原有规范化摘要。
不修改线上 bucket 的保留策略，也不声称具备第一种保证。正常快速续跑仍须
验证原子交接、租约、STOP 和已接受的原始事件，不能仅删除恢复证明。

## 当前实现与升级约束

- 新模式的预算预留不重读无关历史 checkpoint；结算仍验证当前原始响应。
- 提交仍回放完整原始 MODEL 事件和预算事实，但物理 checkpoint 校验只覆盖
  当前记录的全部 part；生命周期枚举也采用相同范围。全局数量/字节上限保留。
- 独立认证、报告读取、故障恢复和重建不传增量范围，仍完整校验原始证据。
- 不使用可被篡改的 `record_ids` 提示过滤接受批次：被排除的批次可能包含
  当前记录的重复依赖。该试验已撤回，批次定位须另有完整性绑定后才能优化。
- Worker 协议升级为 `validation-mode:v3`，API 与 Worker 的配置摘要共同绑定
  此版本，v2 Worker 无法接收新要求。既有 v2 pending 命令不能直接由 v3 接手；
  切换前须保留旧 Worker 排空旧任务。没有自动重写持久命令或自动部署。
- 未指定模式的任务仍为 eager；其规范化 JSON 不增加默认字段，历史摘要不变。
- 该模式不代表正常续跑、查询复杂度或端到端性能目标已完成。
