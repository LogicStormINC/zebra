## Actual local broker acceptance

Broker: `rabbitmq-infra-acceptance-rabbitmq-1`, separate network and named volume,
single node on this Mac's Docker engine. No model or user data was involved.
Synthetic messages use only envelope fixtures and random transport message IDs.

`ZEBRA_RABBITMQ_LIVE=1 .venv/bin/python -m pytest -q tests/integrations/test_rabbitmq_live.py`
passed **8 tests in 8.38 seconds** for the final Zebra adapter. Same suite imported
Trench's actual adapter and passed **8 tests in 7.89 seconds**. These are 8
scenarios per adapter, not 16 distinct business acceptance scenarios.

| Scenario | Verified result |
|---|---|
| Both system queues | Confirmed persistent publish, correct fixture received |
| Duplicate physical publication | Same message ID delivered twice; transport does not promise dedup |
| Prefetch 1 | Second message held until explicit first ACK |
| Consumer disconnect before ACK | Same body redelivered after a new connection |
| Unroutable publication | mandatory-return causes failure, not false success |
| Cross-vhost/role/topic ACL | Foreign vhost, relay read, consumer DLQ read, wrong topic rejected |
| Broker restart with unacked message | Consumer automatically restored, persisted hint redelivered |
| Stale delivery after restart | Old-channel ACK rejected; cannot settle new-channel message |
| Capacity pressure | Temporarily lower named test queue limit; publish fails, policy restored |
| Delivery-limit emergency quarantine | Requeues bounded; valid test hint reaches restricted DLQ |
| Topology/metrics | Quorum durable queues, explicit at-least-once policy, metrics available |

## Boundaries and remaining gates

This is **not** Trench Turn/Zebra command runtime integration, PostgreSQL
Outbox/Inbox acceptance, model first-token improvement, browser E2E, production
rollout or HA evidence. No publish/consume application feature flag is enabled.
Trench full-repository and frontend tests were not run; its adapter was checked
with targeted unit and real broker suites. Zebra full-suite result is above.

Next stage must implement atomic Outbox and fenced Inbox/lease handoff,
claim-by-ID, out-of-recency recovery, bounded execution slots, default-off
composition, sanitized rejection, third-party AMQP log filtering and rollout
fallback. Public adapter exceptions are sanitized; third-party diagnostic logs
must not be assumed sanitized merely because exceptions are wrapped.

The local 24h quarantine TTL/queue budgets are fixture values, not an approved
production retention policy. Production needs TLS, managed credentials, three
quorum nodes and failure-domain tests before deployment.
Confirm failure/timeout means unknown transport outcome: retry same message ID
from durable Outbox; neither confirm nor ACK means business completion.
