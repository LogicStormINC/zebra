## P0: actual filesystem isolation before private files or scripts

### Native semantics and why a config-only switch is insufficient

Cloud source root for references below: `/Users/lukeding/Desktop/playground/2026/product/zebra-agent`.

- `apps/api/src/zebra_agent_api/app.py:create_session`: `workspace_source` creates a native pending workspace with fixed quota 256 MiB and `owner_session_id=None`, then stores `workspace://<workspace_uuid>` in the Task preparation. This is a workspace instance UUID, not the Host `workspace_ref`, Task UUID, or conversation ID.
- `packages/agent-runtime/src/agent_runtime/workspace_provisioner.py:_volume_path`: root layout returns the SAME configured directory for every instance; default layout returns `volume_root / str(workspace_id)`.
- `provision_existing` returns existing non-pending rows without rematerializing. For pending rows it transitions to provisioning and calls `_reset_target` before materializing. A mount point is emptied without unmounting; a normal directory is recursively removed. No quota volume allocator/hook was found in this provisioner.
- Host-reference sources create an empty target plus `.zebra-host-reference`. They do not copy ERP data, prior workspaces, or shared files. Archive/snapshot materialization has traversal/link guards but still requires independently authorized source selection.
- `workspace_runtime_resolver.py:resolve_ready/_require_materialized` uses the durable existing `volume_ref` for ready/sealed instances. Changing the configured root does not migrate old Tasks.
- `workspace_quota.py:require_workspace_quota` requires the resolved workspace root itself to be a mount point, with actual `statvfs` capacity at most the configured maximum. An ordinary UUID subdirectory fails closed. Do not disable this check to make private scripts run.
- `adapters/oci.py:_create_command` binds only the resolved workspace into `/workspace`, uses a read-only container root, non-root UID, dropped capabilities and `--network none`. Its normal security boundary must remain intact.

### Target layout and knobs

Use a NEW SIBLING root `/var/lib/zebra/erpnext-private-workspaces`, not a child of the legacy shared root. Otherwise old Tasks, whose root is the legacy directory, can traverse new private UUID directories through native file tools.

For the isolated ERP Worker only:

```
ZEBRA_WORKSPACE_VOLUME_ROOT=/var/lib/zebra/erpnext-private-workspaces
ZEBRA_WORKSPACE_VOLUME_LAYOUT=per-workspace
ZEBRA_RUNTIME_CLASS=gvisor
ZEBRA_RUNTIME_DEFER_PROVISION=true
ZEBRA_RUNTIME_REQUIRE_WORKSPACE_QUOTA=true
ZEBRA_RUNTIME_WORKSPACE_QUOTA_MB=10240
```

Current composition enables root layout only for the literal value `root`; `per-workspace` selects the existing default UUID path behavior. Confirm this against the pinned image before deployment. Retain the legacy root mount and its durable references at the original path for preservation; retention does not authorize new execution there. Mount the NEW root at the identical absolute path into the Worker with host-to-container child-mount propagation `rslave`; the host parent needs an appropriately shared bind mount. A private Docker bind does not expose later child mounts. Do not change Trench mounts or propagation.

Compatibility correction after live verification: the global quota env is currently unset, but `load_settings().runtime.workspace_quota_mb` is **10240**. `runtime_factory.build_runtime` applies that global capacity check to EVERY resolved workspace before runtime construction, including legacy ready paths. Setting it to 256 would reject the existing approximately 1 GiB legacy filesystem. Keep the effective global ceiling at 10240; do not disable quota enforcement. The global value also enters `SandboxSpec.digest`, so unnecessarily reducing it to 1024 introduces additional specification drift. New private UUID filesystems still have a physical 256 MiB limit, checked independently against the native instance's `quota_bytes` by the allocator receipt and private-workspace hook. This global compatibility ceiling is not the reservation or physical allocation limit for new workspaces.

Keep loop backing files outside both roots, for example `/opt/erpnext/zebra-agent/private-volumes/<uuid>.ext4`. Each UUID receives its own persistent 256 MiB ext4 filesystem, mounted `nosuid,nodev`. Scripts may use an interpreter against workspace files; do not add direct network access or secrets. Parent directory is root-owned and non-writable to UID 65532; each mounted filesystem root is owned by the sandbox UID/GID. The Worker must not be able to replace sibling mount points.

### Small trusted automatic quota provisioner

No existing allocator can satisfy the per-instance mount requirement automatically. Implement one isolated ERP operator component, not browser-supplied shell commands and not CAP_SYS_ADMIN inside Frappe/Worker/sandbox.

1. Expose one fixed operation `ensure_workspace(task_uuid, request_uuid)` on a root-owned local operator service. Accept no path, mount options, size, source URI, user, namespace, or executable from the request. Frappe's authenticated BFF calls it after native Task creation and before first run. Scheduler uses the same operation before dispatching a new scheduled Task.
2. Use a dedicated workload credential, separate from Host tool HMAC and signing keys. Authenticate the fixed endpoint with canonical request HMAC, timestamp, nonce/request ID, bounded body and replay records, over the isolated integration TLS route or a protected local socket. The caller derives Task UUID from the owned conversation. Browser calls never reach this endpoint directly.
3. Independently load authoritative native Task binding, active segment, and its workspace projection or immutable `TASK_PREPARED.workspace_root`. Require deployment `erpnext`, expected issuer/Host/namespace, exactly one principal, and the NEW private workspace generation. Resolve exactly `workspace://UUID`; join that UUID to `PostgresWorkspaceControlStore.get`. NULL `owner_session_id` is NOT proof of ownership. Check expected Host source locator and binding against the authenticated ERP ownership attestation/current permission check.
4. Allocate only a fresh PENDING, host-reference workspace in the new generation. Reject legacy root references, arbitrary sources, unknown/uncertain/provisioning/released rows, existing foreign mounts, symlinks, and mismatched source/quota facts. Do not fix the inventoried old pending/uncertain rows as a side effect.
5. Derive both target and image paths exclusively from canonical UUID plus fixed roots; verify parent ownership and `lstat` components. Use argv arrays, a per-UUID lock and global allocation lock. Persist operation state so retries return the same allocation and never reformat an existing filesystem. A lost ACK must not recreate, clear or enlarge its volume.
6. Reserve a fixed resource ceiling before allocation: proposal is 256 MiB per workspace, at most 32 active allocations / 8 GiB reserved, plus a host free-space floor chosen from current disk inventory. Count orphan/in-progress images against the ceiling. Fail visibly when capacity is exhausted; do not prune active or historical data to recover space.
7. Create/format only a new service-owned image, mount at the derived UUID path, verify mount source identity, filesystem UUID, capacity and flags, and persist a content-free receipt. For a repeated ready allocation only verify; never format/reset. Native Worker subsequently owns materialization/state transitions and writes its durable `volume_ref`.
8. On restart, restore mounts from the operator's protected manifest BEFORE starting the Worker. Refuse manifest/path/source mismatch. Never run a broad recursive cleanup. Retention/removal is a separate authorized lifecycle, with checks that no active native instance uses the volume.

An automatic bounded operator is a necessary isolated deployment addition; there is no honest config-only per-Task quota allocation in the inspected image. Its read-only PostgreSQL access, if used, should be restricted to necessary ERP deployment facts; do not hand broad DB credentials to script sandboxes. If adding a service is undesirable, a narrow native provisioner composition hook is the alternative, but it requires a reviewed Cloud change rather than silently claiming existing support.

### Preferred race-free admission hook and exact native proof

After discussing admission ordering, prefer a tiny root-owned Unix-domain-socket operator over a public HTTP allocator. Mount its socket and dedicated HMAC credential into the Worker composition only, outside every workspace and OCI sandbox. Check UDS peer credentials against the configured Worker host UID (verify user-namespace mapping rather than assuming it), AND canonical HMAC/timestamp/nonce. Use a fresh authentication nonce for retries and a stable operation request ID for idempotent allocation receipts; replay protection must not prohibit recovery of the same allocation after lost ACK. Bound JSON, timeout, client concurrency and resource reservations.

Add an opt-in native hook in `WorkspaceRuntimeResolver.resolve(reference, session_id=...)`: after resolving/validating the workspace UUID and loading its existing instance, and BEFORE calling `provision_existing`, call the trusted allocator only for a NEW private-generation PENDING instance. Do not wait for a poller to notice PENDING rows. Do not call after `PROVISION_START`: unknown transport outcomes should retain PENDING rather than turn normal allocation recovery into native UNCERTAIN materialization. After allocation, verify exact mount/capacity, then let the unchanged native provisioner perform reset/materialization/transitions. A missing/bad allocation receipt must fail closed before reset. READY/SEALED paths keep existing durable volume refs and never reformat or remount them implicitly.

For NEW-generation private READY/SEALED paths, validate the already allocated filesystem identity, expected derived path and `require_workspace_quota(..., maximum_bytes=instance.quota_bytes)` on every resolution/continuation as well; do not recreate it. Only allocation is PENDING-only. This prevents a later oversized or wrong-source remount from passing merely because the global legacy ceiling is 10240 MiB. Legacy-generation ready paths retain the existing global check and must not be subjected to the new 256 MiB private-instance check or silently granted new capabilities.

Request shape should include `{session_id,workspace_id,request_id}`. Independent proof can use native stores or a bounded read-only joined query:

1. `execution_segments(deployment_namespace,session_id)` gives task_id.
2. `agent_tasks` must match that task and have `active_segment_id = request.session_id`.
3. `workspace_projections` for the same namespace/session must reference exactly `workspace://<request.workspace_id>` (native path normalization also accepts `workspace:/<uuid>`). If a projection is unavailable, use its immutable TASK_PREPARED source facts; never infer from user-supplied filesystem paths.
4. `workspace_control_instances` for the SAME namespace/UUID must be PENDING, 256 MiB, host_reference, and have the server-owned NEW private source generation, for example a versioned `erpnext://private-workspace/v1/...` locator. Old pending/uncertain sources must not become eligible just because configuration changed.
5. Load the latest `task_binding_snapshots` row by descending binding_revision and validate its typed Task binding digest, Host issuer/app/namespace, single principal, Host workspace ref and current authorization facts. Native `PostgresDirectControl.load_task_binding` provides the existing typed read. Do not trust NULL `owner_session_id`, or a JSON claim without binding consistency validation.

The hook and allocator only prepare storage; they do not create/dispatch Tasks, execute models, mark workspaces READY, or authorize business data access. The same Worker resolution hook naturally covers scheduled admissions, which create and immediately submit native Tasks without an intervening Frappe BFF call. This resolves the P5 allocation race without a second queue or manual per-future-user mounts. BFF may preflight/ensure before run for faster failure, but Worker hook remains the execution gate.

### Prerequisite: live ERP revocation at real execution boundaries

Read-only audit of the DEPLOYED schema-105 Worker found no live ERP permission revalidator for generic native operations. This conclusion is based on deployed source inspection, not local schema-107 assumptions:

- `bound_execution_authority.py:BoundHostExecutionAuthorityResolver._fail_closed_checks` checks bound issuer, namespace and Host grant expiry. Its synthetic `ExternalAuthorityGrant.revoked` is always false. It does not call ERPNext or inspect current User.enabled/Company permission.
- `runtime_authority.py:persist_attempt_authority` persists typed authority evidence at Attempt start/resume. It is not called before every tool/model dispatch. `context_materialization.py:prepare_worker_context` selects/persists this authority before context materialization.
- `select_attempt_authority` replaces the deployment resolver with `BoundHostExecutionAuthorityResolver` for a bound Host Task. Merely injecting a fresh global resolver would therefore not fix these Tasks.
- Deployed `DurableHarnessEventRecorder.require_active_execution` reads Cloud Session state and checks lease ownership. Deployed `WorkerToolGateway.execute` directly delegates to `_execute`. These are native cancellation/ownership boundaries, not proof that ERP permissions remain valid.
- ERP Host gateway already checks the mapped user and current Company read permission. Native file reads, attachment/context use, private commands, model requests and MCP calls can bypass that Host gateway while their frozen Host JWT remains valid. Extension-version revocation checks are a different boundary and do not close ERP-user/company revocation.

Do not advertise P3/private-data revocation acceptance until a real fresh Host boundary is composed. Add a fixed authenticated TLS BFF authority probe for this isolated ERP Host; do not expose arbitrary authority URLs, browser user IDs, or a fake lease refresh.

Probe proposal:

1. A configured fixed Host endpoint receives a bounded canonical request containing native Task/session/run coordinates, binding digest, current bound grant ID, operation kind and non-secret tool/model/target metadata. Use the existing fixed workload HMAC/TLS pattern with exact method/path/body, separate authority purpose/identity, timestamp/nonce and bounded response/timeouts. Keep its credential in Worker composition outside every workspace/OCI sandbox. Do not place original JWTs, API keys, cookies or private tool arguments in audit output.
2. BFF resolves the issued Grant record itself, then its conversation/fire mapping. It checks non-expiry, exact principal/host/namespace/workspace/run/company consistency, active run/stop state, enabled ERP User, fresh `Company.check_permission('read')` under that user, and published capability/preset/connection/resource authorization. It also applies the P0 legacy shared-root observation-only rule using native workspace generation/materialization evidence: a valid old grant/lease does not authorize new generic execution. Clear/request-scope native permission caches as appropriate; a previously cached administrator result cannot authorize a different user. Unknown mapping, drift, revoked membership, disabled user and timeout fail closed.
3. Response supplies content-free current authority evidence: allowed/revoked/denied, checked time, bounded expiry, policy/source digest and precise reason code, with identities matching the request's authoritative binding. It grants no new capabilities, no new principal/workspace and no longer lifetime. TLS authenticates the fixed Host; response identity/digest must still be checked rather than treating any HTTP 200 as authorization.
4. Compose this revalidator AFTER the Task-bound resolver has been selected. Preserve the bound resolver's immutable ceiling/issuer/expiry checks; a thin opt-in Host adapter delegates to them and narrows through existing `ExecutionAuthorityResolverPort`, `ExecutionAuthorityRevalidationRequest`, `ExecutionAuthorityRevalidation`, `ExecutionAuthoritySnapshot.ensure_not_expanded` and decisions ALLOWED/NARROWED/REVOKED/DENIED/EXPIRED. Do not replace these contracts with a boolean that omits durable evidence. The same-Attempt expiry cannot be extended; only an independently verified new API command binding may start renewed evidence through the existing renewal seam.
5. Invoke the shared guard before context/private attachment materialization and before every actual model request (including retries/compaction/title helpers), generic tool dispatch, command execution, MCP credential release/request and private artifact publication. Wrap the per-execution model gateway and shared Worker tool boundary or add an equally narrow opt-in callback at those existing seams; do not patch one named ERP tool and leave sibling file/MCP routes unchecked. Native cancellation/lease fencing runs as well and remains authoritative.
6. Every relevant new dispatch requires a fresh probe, not a positive result cached across boundaries. Serialize durable revalidation evidence using the existing fenced recorder mutation path; parallel tool checks must not create a journal sequence race or share an unchecked stale snapshot. Bind accepted evidence to the exact prior snapshot/binding and recheck local fence before dispatch. On denial persist the typed outcome and stop further dispatch; do not change request IDs or rerun business work to recover. Provider/network unavailability is a visible fail-closed authority error, not an allowed fallback.

Revocation race statement: authorization linearizes at the fresh Host check immediately preceding dispatch. Revocation after that instant may race an already-started model/network/process call; no plan can claim to undo information already sent or an external side effect already committed. Reuse native cancellation/transport checks to stop in-flight work when denial becomes known, reject later model/tool/publication boundaries, and retain uncertain-effect evidence rather than blind retry. This is distinct from guaranteeing the NEXT not-yet-authorized dispatch is denied. Private sandbox scripts keep network isolation even during this race.

Minimum runnable regression: with Cloud Session/Worker lease deliberately still valid, a fake Host allows boundary one and revokes boundary two. Assert the second files.read, command, MCP mock request and model request each cause zero downstream calls, typed denial evidence references the prior snapshot, and the original tool/effect idempotency key is preserved. Add timeout/malformed/drift fail-closed, no-expiry-expansion and parallel-journal cases. Real isolated-user acceptance removes Company permission/disables the disposable user between two dispatched operations; verify the next relevant native file/MCP/model operation is denied without waiting 30 minutes or restarting Worker. Restore only the QA fixture configuration afterwards.

### Native extension contracts

- Scope is exactly `(authority_issuer, namespace_id, principal_id, workspace_id)`, derived from verified grant. This already supports owner/company isolation when the Host workspace ref includes user+company+site. Scope derivation is deployed, not merely local.
- `GET /v1/extensions/skill-installations` and `/mcp-connections`: `extensions.read`; query `limit,cursor`. Detail path uses an opaque installation/connection ID.
- `POST` those collections: `extensions.manage` and stable `Idempotency-Key`. Skill body `{skill_id,version_id}` references an already published package; MCP body `{endpoint,transport:'streamable_http'|'sse',auth_mode}`. Created configurations are initially disabled.
- `PATCH /v1/extensions/<collection>/<id>`: `If-Match: "<revision>"`, body exactly `{enabled:boolean}`. No endpoint edit or arbitrary field patch. Credentials use separate POST/DELETE `/mcp-connections/<id>/credentials`, If-Match; POST body exactly `{token}`; native response never returns the secret.
- POST `/mcp-connections/<id>/refresh`, If-Match, empty body; GET `/.../catalog` returns the discovered catalog. Catalog refresh must use native SSRF/credential boundaries, not a browser-supplied URL.
- Skill publication collection is `/v1/extensions/skill-packages`; use existing native publication and install services, not raw trusted skill text supplied by a user.
- At Task creation `skill_components` contains permitted published **skill IDs**, frozen as the ceiling. Per AG-UI run use explicit top-level `extensionSelection:{plugins:[],skills:[installation IDs],mcp:[connection IDs]}`. An explicit empty selection means none; omission retains legacy automatic enabled selection and can unintentionally broaden selection.
- Existing tasks created with empty Skill ceiling cannot gain arbitrary new Skills through a turn picker. Preserve history and explain successor behavior. Native snapshots/revision checks must reject revoked or changed configurations at the next relevant execution boundary.
