## Product behavior and proof boundary

Fresh authorization precedes completion/progress/private-input recovery. A denied, revoked or expired authority ends this original unstarted command, without a fake AttemptStarted, handled Event, terminal Run/Turn Event, prior authority snapshot, business effect, model call, or publication. The canonical Task/Turn remains unchanged. Read-only outcome metadata says why dispatch did not begin.

Temporary unavailable on modern delivery records a known pre-execution outcome, releases the lease via the native RetryableWorkerSetupError boundary, and uses existing bounded native recovery. This is bounded re-entry before authorization; an allowed later probe may enable the original command's first execution. It is not described as a probe-only retry or permission to replay business work. Native limits remain generation ceiling 5 (initial generation 0 plus at most five recovery approvals, 0..5), 24-hour total age, 60-second base delay and existing capped exponential backoff. A released lease is still deferred while its original expires_at remains in the future; release does not promise an immediate retry. Classic delivery has no such durable retry budget: unavailable stops this command using its exact rejection receipt and offers the explicit action below.

Permanent refusal or exhausted temporary retries expose **重新验证并继续原请求** only when the whole current Turn is proven never executed. Only an explicit human action invokes it. It creates a fresh Host Grant, new Run identity, new command and latest expected revision, then invokes native RUN for that same canonical Turn. It does not append the user message, cancel, roll over, or revive the original command. A started or uncertain Turn never offers or accepts this action. In particular clarification/approval/client-effect continuations with earlier real execution are outside this recovery promise: fresh still fails closed and native Stop/reconciliation/control remains available, but no no-effect seal or same-Turn rerun is fabricated.

## Native execution seam and typed errors

Both classic execute_session and modern execute_claimed_session converge on execution_recovery._execute_with_heartbeat. Introduce a narrow optional refusal callback through these existing entry points and their lease wrappers. It receives the actual WorkerLease and a typed early decision; it runs inside the live heartbeat before lease release. The runtime consumer remains lease-only; the modern command_process wrapper closes over its dsn/namespace and actual capability. Classic closes over its validated immutable accepted SessionEvent.

Only the initial fresh seam emits the new types. Permanent early refusal must not inherit WorkerExecutionError. Temporary early unavailability uses a dedicated RetryableWorkerSetupError subtype, caught before the general retryable branch to persist its metadata and then re-raised. Generic runtime revalidation and exceptions after start keep their current behavior. No broad ValueError conversion is allowed. Expected native HostGrantExpiredError/ScopeError/MismatchError and explicitly typed stored-binding failures may be classified; arbitrary loader, SQL, programming or malformed native lineage failures remain unclassified and fail closed without a false refusal claim. A bad stored snapshot still blocks Host probes and private reads even when its corruption prevents safe command attribution.

Policy codes are a small fixed allowlist: permanent refused, temporary unavailable, and temporary retry exhausted. The precise bounded probe reason may be retained as a second fixed enum, never exception or transport text. HTTP 401/403 from the pinned authenticated endpoint is refusal; HTTP 408/425/429/500-599 and specifically identified HTTP timeout/connection transport failures are unavailable. Other HTTP failures (including redirects), malformed/oversized body, invalid response shape, generic probe_unavailable and unexpected internal exceptions are unclassified fail-closed errors; they do not receive a known permission or automatic retry classification. Because the general gateway may label a caught ValueError transport_error, that string alone is not proof of a retryable network failure: retain the narrow typed HTTP transport category at the private probe boundary, without adding another business transport. An explicit local stored-binding expiry, locally validated authority/profile revocation, or a well-formed allowed response whose identity/digest differs is permanent refusal. This classification is local to the ERP control probe; no general Host Tool retry policy changes. Native gateway metadata exposes http_status and bounded reason; image provenance of its capture must be checked before relying on that interface.

## Shared metadata proof and atomic writes

Reuse control_plane_idempotency_records for a narrow ERP fresh-disposition proof, using one fixed action and key `<accepted_event_uuid>:<generation>`. No schema/table/event/queue is added. Each record is immutable and binds deployment namespace, principal/tenant/workspace/scope key, canonical accepted Event fingerprint, native command payload fingerprint, modern canonical envelope digest, command/session/Task/Run identity, original Turn identity/opening sequence, current generation, exact lease fence, execution floor, fixed outcome/reason and DB observation time. Classic has no broker envelope and explicitly uses its exact canonical Event plus native command fingerprint instead. Do not store command text, credentials, business payloads or raw Host responses in response_body. The existing request_hash is computed from the exact canonical Event using the existing fingerprint logic, and the table namespace must equal the proof namespace.

Extract PostgresIdempotencyStore's existing save body into a transaction-capable helper; save itself delegates unchanged. Reuse that helper, not duplicate its SQL. Conflicting existing response metadata or fingerprint must fail rather than silently return an unrelated record. Classic also writes its existing worker.legacy-command.rejected.v1 receipt in the same transaction, preserving its original command fingerprint and scan exclusion.

Proof transaction ordering follows native lease/stream/command/Task boundaries. Resolve exactly one modern accepted receipt from full namespace/session/fence (or classic's supplied accepted Event), then validate canonical command and Run attribution, Task lineage, scope, generation, current Inbox/outbox, retirement/control absence, and native recovery approval. Lock lease authority and assert it remains current; lock stream and command rows. At initial persistence require current stream equals the execution floor, after accounting for native MESSAGE admission already committed at handoff. Require started_event_id and handled_event_id null. Verify the complete contiguous native approval chain from generation 0 to current, exact previous/current message identities and receipt snapshots: missing/duplicated/out-of-order history or any earlier started/handled/uncertain receipt fails, even if current rebinding cleared its columns.

The current Turn also must never have executed: identify its canonical human USER_MESSAGE_RECEIVED using only metadata fields (origin, actor, turn_id, turn_index, sequence) and prove no HARNESS_ATTEMPT_STARTED, execution authority/progress/effect dispatch, terminal or conflicting Turn evidence after that opening. Old completed Turns may exist; they are outside this interval. The complete post-opening allowlist is: (a) exactly the canonical root TASK_PREPARED at sequence 2, actor HARNESS, only when the opening is root sequence 1/turn index 0; (b) validated SESSION_COMMAND_ACCEPTED metadata for RUN on this Turn, including earlier sealed refused RUNs and the current command. No other post-opening event type is allowed. In particular title, resume, clarification, control, handoff, worker preparation, authority and effect events fail the safe-explicit-retry proof. This conservative ceiling is intentional; no private payload recovery is invoked to soften it.

Native initial admission is SESSION_CREATED(0), USER_MESSAGE_RECEIVED(1), TASK_PREPARED(2), then RUN acceptance. Follow-up HTTP input opens the next Turn with one USER_MESSAGE_RECEIVED, then RUN acceptance. Task binding renewal and extension snapshot binding are table metadata, not extra SessionEvents. A native MESSAGE handoff creates its one human input after acceptance, so its accepted MESSAGE may precede the opening; validate that exact causation/input_event_id association separately, and allow subsequent RUN acceptance as above. A clarification RESUME is excluded by the existing prior execution evidence. These facts are from session_bootstrap.py, session_messages.py, http_input_messages.py, command_wakeup_message.py and extension_turn_admission.py; regression cases must execute the native initial/follow-up/MESSAGE variants.

Reuse pin_command_consumer semantics: it is mandatory only for native strict requirements, and ordinary non-strict ERP commands retain native None behavior. Re-pin under final Task authority lock and check DB clock after writes. Assert the lease fence again immediately before commit. Expiry or drift rolls back every tentative proof/pending/classic-rejection write. Heartbeat then releases normally. Uncertain or already-started cases receive no not-executed rewrite and remain on native recovery/uncertain handling.

Modern permanent: proof + pending.status=dead/recovery_code=refused atomically; accepted receipt/Inbox/outbox/events/binding remain untouched. Modern temporary: proof + pending.status=pending/recovery_code=unavailable and native delayed recovery_due_at. Classic permanent or temporary: proof + exact existing rejection receipt; no automatic same-command revisit.

## Modern native bounded recovery

PostgresLeaseStore.release sets released_at and retains the fence row. Existing _recover can approve expired_unstarted only when the same retained fence, no started Event, and no post-floor Event remain; lease absence/replacement or execution evidence keeps native uncertainty. Preserve those conditions and all normal/strict recovery behavior.

For a fixed unavailable code, validate the sealed current-generation proof under the same recovery locks. Save its fixed outcome/proof identity in the existing previous_receipt JSON audit snapshot when a recovery generation is approved. Keep native reason=expired_unstarted (the factual condition); do not rename it to a crash. The new generation remains subject to the original budget and fresh-first execution.

At native budget exhaustion, only an exact still-valid unavailable proof may produce pending.dead/recovery_code=erp_fresh_authority_retry_exhausted. The proof was originally committed under a live fence; exhaustion does not manufacture a new live-fence claim. The current retained fence and unchanged floor must still match, and the full earlier generation history must remain unstarted. Otherwise use the existing reconciliation/exhaustion behavior and do not offer explicit rerun.

## Prior-command gate: proof, not arbitrary recovery_code

Extend the existing handoff prior-command exclusion to recognize only terminal ERP fresh disposition supported by the immutable proof plus exact canonical command/receipt/generation/Turn associations. It must reject free-text dead codes without proof, corrupted fingerprint/proof, started/handled receipts, expired/replaced association or uncertain recovery history. Reuse one focused verifier for public retry eligibility and prior-command gating.

Historical seal validity and current retry eligibility are different questions. For historical prior gating, validate the sealed opening-to-floor interval and its immutable original identity. End any subsequent interval at the FIRST validated successor command admission in that Session, regardless of whether that later command is RUN, MESSAGE or a control command; do not require that historical successor to name today's Turn. Unexpected execution evidence between the sealed floor and that first successor is an integrity conflict. Once that canonical successor exists, its later legitimate execution, closure and new human Turn do not invalidate the old refusal. A third command and subsequent normal MESSAGE/new-Turn flow must continue to skip the old sealed refusal after a successor completes. Never compare the old floor to today's whole stream or require today's Turn to remain unstarted for historical gating. This is acknowledgement of the old non-execution outcome, not authority for the successor: all native successor admission/Turn/control rules remain active.

Current explicit retry eligibility additionally requires that the requested refused Run is still the latest applicable command, the same Turn is still current, there is no accepted successor or unknown dispatch, no active lease, and the whole current Turn remains within the safe allowlist. The successor independently satisfies current VerifiedHostGrant admission, immutable binding renewal and the Worker fresh probe. A proof grants no execution authority. Receipt handled/start columns remain null; old Run history remains unchanged.

The native AG-UI path already renews Host binding from a fresh verified Grant before command admission. session_binding preserves principal/workspace/thread/issuer and ceilings, permits new Run coordinates, and appends an immutable revision. Existing RUN admission uses current_turn and can reuse its original extension snapshot; generic MESSAGE admission must remain unchanged.

## Explicit BFF RUN action and lost acknowledgement

Add one small whitelisted retry RPC backed by the existing per-conversation submit lock, ownership and Company permission checks, admission pause, and fresh header/outcome read. Its request includes the rejected Run/accepted Event identity and a client-generated operation UUID. Reject stale/current-Run mismatch, arbitrary action payloads, started/uncertain work, unrelated user/company and concurrent submission. It uses the original stored request options and existing Turn; no user message, attachment or model-setting mutation is accepted.

Reuse existing pending_command as the durable pinned command body and existing request coordinates for crash/lost-ACK recovery. This has two explicit local phases in existing JSON request metadata, not a new scheduler/table: first persist operation UUID, predecessor refusal identity, new Run and phase=preparing BEFORE grant or client-surface network mutations. Retain the predecessor as the visible active Run until command dispatch is ready. Client release/open uses that same operation/new-Run intent, including native opening_run/opening_at unknown-response fencing (420 seconds); no retry clears this fence, allocates another Run, or assumes an opening failed. Grant or client preparation has no automatic business dispatch.

Only after a valid same-Run client surface is known, obtain the latest header revision and materialize the immutable complete RUN body in pending_command, set phase=dispatching and new active Run, and commit BEFORE the AG-UI POST. The native idempotency key derives from the operation UUID. Repeated operation UUID resumes the same phase/body or returns its accepted result; a different UUID while either phase is unresolved is rejected. Unknown AG-UI acceptance retains the exact body, expected revision, Run and key: query/reuse it, never rebuild it from newer state. Duplicate clicks, timeout after accept and refresh/retry must yield one new command and Run.

Known pre-accept permission/validation/revision rejection is different from an unknown response. Restore the predecessor active Run and expose its blocked outcome, preserve the rejected operation's immutable metadata, and clear only the command whose non-acceptance is proven. A repeated rejected operation returns the same known result; a new explicit operation may revalidate later. This prevents a new unaccepted Run lookup from hiding the predecessor refusal and Stop UX. A timeout/5xx/ambiguous receipt does not authorize this restore/clear. The active Run, pending marker and error classification are rechecked under the same conversation lock after each network boundary.

The RUN input contains no new messages and no resume token; native _command_payload permits empty input/messages. Preserve applicable original extension/client context through existing server-held metadata and reopen/rebind the existing native client surface for the new Run when needed, without copying an old Run's credential authority. A successful fresh grant and native command acceptance changes the Host coordinate to running; authorization denial retains an honest blocked outcome. No auto cancel, rollover, or business replay occurs.

The current AgentRunStatus usage does not wire any available-action callback. Prefer a single existing-style button rendered from the fixed retry action near status, calling this RPC through the existing api helper, then existing snapshot/watch reconciliation. Disable it during submission and use the same view/conversation guards. No UI redesign or new dependency. Preserve pending operation identity across lost responses using the existing server pin; a new page may query/reuse that pin rather than create a new operation implicitly.

## Required runnable acceptance

1. Actual classic public consumer + real LeaseHeartbeat: exact canonical receipt, repeated scan exclusion, temporary/permanent codes, late-fence rollback, zero private readers/attempt/model/tool/publication/terminal writes; STOP/CANCEL unchanged.
2. Modern real PG accepted handoff and proof transaction: exact capability/fence, immutable history, metadata-only result, idempotent replay, concurrent writers and late capability/fence expiry rollback. Started receipt, hidden earlier-generation start, post-floor event, effect uncertainty and malformed proof all forbid retry eligibility.
3. Temporary modern released-fence recovery: existing delay/generation budget, known outcome carried in previous_receipt, fresh denial before private read on each generation, first execution only after allow, exhaustion visible without crash fiction, no automatic business replay.
4. Native successor RUN after sealed permanent/exhausted refusal: old receipt not handled, same original Turn/message, new Run/command, new binding revision and current Grant, exact latest revision; no new USER_MESSAGE_RECEIVED. Wrong-scope/new-Run mismatch and started/uncertain Turn are refused.
5. Authorized header + AGUI SSE + BFF cold snapshot expose both classic and modern codes without changing canonical Task status. Explicit button/RPC grant failure, unknown client release/open, its existing 420-second opening fence, AG-UI lost-ACK, duplicate, stale view and known pre-accept grant denial remain one-command/one-Run with predecessor outcome recoverable. A third command after the successful successor and a later ordinary MESSAGE/new Turn must not become blocked by the historical refusal. No implicit resend.
6. Existing fresh, containment, continuation, HTTP input, control and UI checks remain green; disabled fresh/non-ERP behavior unchanged. Isolated real PostgreSQL proves transactions/locks; assertion doubles alone do not. Native containers remain network-none and model/business endpoints forbidden. No deployment or activation is claimed from source checks.

Native RUN facts: AG-UI _command_payload accepts omitted input and fills messages/state/tools/context with empty values; action=run forbids a resume token. SessionCommand RUN has no requirement to append a message. command_submission passes existing_turn=True, and extension_turn_admission requires current non-legacy Turn then reuses its prior extension snapshot digest. Native renewal occurs before this admission and permits a new Run coordinate within frozen ceilings. Thus same-Turn RUN has a native surface; runnable acceptance must still exercise it with the actual public API, metadata store and existing client-surface flow before activation.

Place shared proof writing/reading/verifying in agent-storage's PostgreSQL command support, using agent-core native types and no Worker imports. Worker and API compose this shared helper; BFF consumes only the authorized fixed public outcome. Do not introduce a general authority/recovery framework. If runnable native public acceptance reveals an additional gap, report it rather than weaken this proof.
