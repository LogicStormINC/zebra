# ERPNext + Zebra Agent 全功能扩展设计

状态：范围已由用户明确为“ERPNext 全业务能力 + Agent 通用功能”；本文已通过独立设计审核，待用户确认设计。尚未实现或发布本轮新功能。

## 目标与口径

在现有 ERPNext 内嵌助手上，实现当前用户有权使用的已安装 ERPNext 业务功能，以及文件/图片、交付物、联网检索、数据分析、技能/MCP、知识资料、记忆和定时任务的完整可操作入口。复用 Zebra Cloud 的执行、事件、存储和调度权威，不另建 Agent、任务队列或文件执行器。

“全功能”按功能清单逐项验收，不等于取消原生权限、承诺每个客户自定义控制器均自动可用、或把未安装应用/未配置供应商称为已支持。功能状态区分：可使用、需配置、当前角色不可用、执行中、未通过验收。隐藏功能按钮或仅返回健康状态均不算完成。

## 当前部署事实（2026-10-23 现场核验）

- 已安装应用：frappe、erpnext、zebra_erpnext；466 个非子表/非虚拟 DocType、194 个启用 Report。当前没有激活的 Workflow。
- 已有动态 DocType/字段发现、查询/读取、单据生命周期、工作流通用适配、报表运行、附件/打印、14 个审核过的销售/采购/付款转换。不是 466 个 DocType 或 194 个报表均逐项完成业务验收。
- 浏览器已注册两类前端动作：erpnext.ui.document.open、erpnext.ui.form.fill。当前输入附件上限为 0，成果资源、记忆和调度尚无完整 UI。
- 当前任务 network_profile=none、policy_profile=read_only、tool_profile=research；不是完整联网/分析模式。
- Cloud API 与 Worker 为独立 erpnext 部署，运行中；已部署代码含 schedule、memory、extension、task artifact/usage/attachment 路由。
- 实际 GET /capabilities/runtime 为 200，schema_version=105，支持 none/setup-only/domain-allowlist/mcp-proxy-only/full-gateway/git-proxy-only/full-trusted-local；客户端 surface 合约版本为 1。
- 当前 ERP grant 对 /schedules 的请求为 403 host_grant_rejected；/users/Administrator/memory 返回 200 空对象。路由文件存在不等于权限、存储或执行端到端可用。
- workspace_ref 当前按公司复用。在接入私人附件或知识资料前必须扩展用户隔离，不把这一工作区直接当作私人文件夹。

## 方案比较与推荐

1. **推荐：复用 Cloud 原生能力，补 Host 授权和现有 SDK 界面。** 保留现有 UI/GSAP、会话设置、Native Task 与所有原始 Run，改动集中于本插件、部署配置及必要的原生兼容适配。按下面依赖顺序逐包发布，每包有实际证据。
2. 把全部 ERPNext 按钮交给无约束浏览器/任意 RPC：短期入口多，但缺少稳定的参数、版本、权限和回执边界，不能作为业务写入通道。
3. 重新实现一个 Agent 平台：重复 Cloud 的任务、存储、模型、记忆、扩展和调度，维护成本高，不采用。

## 必须先完成的隔离和授权

1. 新私人任务使用用户 + 公司 + 站点的隔离 workspace_ref；服务端从会话与登录态推导，浏览器不能指定其他工作区。仍可显式设计公司共享资料库，但共享必须经过当前用户资料读取权限，不以“同公司”替代文件权限。
2. 已有 Task 的 workspace/grant 绑定不可直接改写。旧会话历史继续读取原绑定；新私人文件能力只对新隔离工作区开放。若需要原会话继续使用新功能，建立明确的受控后继 Task/映射并关联原历史，保留原 Task/Run，先做迁移验收。不能静默复制所有共享文件或重跑历史业务。
3. 个人记忆、知识资料、成果、MCP 连接和调度要分别验证用户/公司/namespace 范围。若原生 memory 只按 principal 隔离，需要原生支持的公司作用域或受控身份映射及兼容迁移；不直接全局开放自动注入。
4. 调度需要 schedule.read/schedule.manage 等最小 scope、可续期的原生调度授权，以及每次执行时重新检查用户、公司和功能授权。现有 30 分钟 Zebra Grant 不作为长期后台业务写入授权。定时业务写入仍产生待确认提案，不复用旧审批或自动确认。
5. 扩展配置使用独立管理权限，不把 /admin 或任意 URL/RPC 代理暴露给普通用户；服务器路径、密钥和工作负载凭据不回传浏览器。只对 ERPNext 的独立 Host 开通已审查能力，不改变 Trench issuer。
6. 管理类 DocType、凭据、脚本与权限配置不通过取消 RESTRICTED 来实现。逐类发布受控原生动作并保留独立确认；执行脚本的站点管理能力保留给明确的运维流程。

## 不缩减范围的覆盖账本

P0 生成部署版本的可核对能力账本，基础覆盖本次 466 个 DocType、194 个 Report，并盘点安装应用的菜单/页面动作、whitelisted controller 方法、原生映射转换和导入/导出入口。账本每项必须标明：当前角色与适用模块、原生入口、通用适配/专用动作映射、参数与副作用、已验收/待实现/需配置/明确限制，以及原因和证据。只枚举元数据不算把按钮操作接通。

P2 完成条件为账本中的业务操作均有已验收映射，或明确记录当前应用/角色/业务配置导致不可用的原生原因；实现遗漏不能归入“原生原因”。不能只验收已发布的 14 个动作就宣布全覆盖。Data Import、Data Export、业务 Single Settings、用户/角色/权限、工作流定义等管理入口均在账本中逐项列出；可安全发布者采用专用合约和管理员独立确认，任意脚本/凭据操作保留明确的原生运维限制并在最终覆盖结果列明，不能悄然移出范围。

至少覆盖以下安装模块的端到端链（缺失应用/原生配置须记录具体原因，而不是把实现缺口标为不可用）：销售的询价/报价→订单→发货→发票→收款；采购的询价/供应商报价→订单→收货→发票→付款；库存的物料/仓库→领料或调拨→盘点；财务的凭证→应收应付→试算/总账；制造的 BOM→工单→工序/领料→完工；项目的项目/任务→工时→结算；CRM 的线索→商机→客户/报价；资产的取得→折旧→处置；质量与支持的记录→处理→闭环。导入/导出和各报表类型另有独立验收。金额、税、库存、生产与资产记账链使用隔离 QA 站点/公司数据，不在真实业务公司制造测试台账。

## 通用能力的副作用授权

服务端维护已发布能力的副作用分类：只读检索、工作区文件写入、敏感数据出网、外部系统写入/消息发送、ERP 业务写入、管理配置。会话里的能力模式/技能/MCP 选择只在已有服务端授权集合内筛选，不能提升 scope、网络权限、主机权限或 ERP 角色。

默认开放已配置的只读功能与当前用户私有沙箱中的文件处理。敏感内容出网、MCP 写入/消息发送及管理修改必须走原生 Policy/HITL，确认绑定真实用户、公司、工具/连接版本、准确参数/目标、资源范围和有效期。ERP 写入始终经过现有独立业务确认；Cloud 自身的工具确认不能替代 ERP 的批准。拒绝或尚未确认时不得产生对应副作用；确认结果未知时不得换请求 ID 重做。

脚本/技能运行环境不挂载 ERP 配置、数据库密码或 Host 签名/HMAC 密钥；对 ERP 的网络访问只能经过用户范围内的受控 Host 工具，不能把可执行沙箱变成审批旁路。出网按公布的能力/目的地/数据规则，经原生网关阻止本机、内网、元数据地址和其他租户资源。ERP 局域网访问仅为受控 Host 集成留出精确通道。连接授权、用户或公司权限撤回在每次调用/定时触发时重查，撤销连接版本不能被已排队工具继续使用。

验收必须包含：未确认 MCP 写入被阻止；有确认的模拟外部写入只执行一次；脚本不能直连 ERP 私有入口/数据库或执行未经确认的业务写入；用户/公司/连接撤回后已有 Run 的下一次相关工具调用被拒绝。测试外部写入使用专用本地模拟接收端，不向真实第三方账号发送消息。

## 数据与接口方向

- Frappe 继续掌握登录、公司、业务权限、审批及 Host 映射，Cloud 继续掌握执行与历史。不在前端另建消息真相源。
- 新入口按用途增加有限 RPC（附件、任务资源、用量、记忆、知识资料、调度、能力目录），复用 cloud.request。服务端构造固定方法和路径；不提供用户指定任意 Cloud 路径的万能代理。
- 会话偏好增加能力模式/已选技能等版本化值，与 request_options 分离；首次、续聊、失败恢复保持同一请求参数/附件内容摘要。
- 收发附件走原生 Task admission；文件识别、文本解析、模型图像兼容、文件名与大小限制在 Host 与 Cloud 两侧校验。文档内容是资料，不是授权或系统指令。
- 交付物绑定真实 Task/Artifact 身份，正文中的任意 URL 不自动升级为可信附件。历史资源下载必须证明所属 Task 在当前会话授权范围内。
- UI 继续复用 Zebra SDK 和 Trench 的输入/资源/设置模式，沿用当前全屏侧栏与 GSAP/reduced-motion。不要把客户需要的工作流散落为大量技术参数。
- 知识库首先查明原生索引与检索契约；若当前安装只有 files.search，则只能声明文件全文检索，不能冒充语义 RAG。需要的索引模块作为独立可配置能力包接入，在证据满足前不标“已完成”。

## 发布顺序与每包门槛

1. **P0 能力盘点/授权/工作区隔离**：能力中心、可用性原因、私人工作区、最小授权和旧会话兼容。验收隔离后才开放私人资料。
2. **P1 附件与成果/过程 UI**：上传、图片、解析、成果卡片/预览/下载、用量与澄清。验证首次/续聊/刷新和请求幂等。
3. **P2 ERP 业务与页面覆盖**：补查询/报表描述、流程动作、工作流/协作、新草稿/列表/报表/子表页面动作；逐模块发布动作清单。
4. **P3 联网、分析、技能与 MCP**：部署支持的能力模式、技能与连接管理、来源与工作区输出；无供应商/连接凭据时显示“需配置”。
5. **P4 知识资料与记忆**：授权索引、引用、更新/删除、个人/公司范围与跨轮验证；先证明隔离再自动注入。
6. **P5 定时任务与管理完善**：上海时区、原生调度授权、真实触发、运行记录、暂停/恢复/删除和权限撤回。

阶段划分是依赖与发布顺序，不缩减“两者都要”的目标。每包通过后才能对外称该项可使用；待配置/受限项在总清单中保留，而不是藏起来或假称全覆盖。

## 验证与回滚

每包留下最小可运行检查；有非平凡逻辑就覆盖一次失败边界。必须包括：普通角色、跨用户/公司、未确认不写、重复请求不重复、版本冲突、授权撤回、过期 Grant、客户端换页/丢失回执、会话刷新、移动端与 reduced-motion。

真实写入只使用专用 UUID fixtures；不动真实库存/账务/用户权限，不发送邮件/外部消息作测试，不替用户创建业务计划或长期定时任务。定时验收任务应短期、只读、结束后移除；原始 Cloud 审计保留。

源代码、聚焦检查、镜像构建、部署和真实跨服务验收分别记状态。扩展前备份站点数据库与保护配置，逐包记录旧镜像/配置回滚点，保留数据库/卷、原始 Runs、现有五条会话和 Trench/认证服务。任何回滚不得通过删除用户资料“修好”故障。

## 审核问题

- 用户期望的完整范围是否已覆盖，是否还有功能被隐含移出目标？
- 是否误把本地最新 Cloud 代码当成部署契约，或把路由存在当端到端成功？
- 工作区/记忆/知识/定时身份是否有越权或历史破坏路径？
- 是否有不必要的新平台、任意代理或未绑定确认的业务写入？
- 每包是否能独立演示并由下一包复用，完成证据是否具体？
