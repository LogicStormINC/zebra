# Dedicated ERP Cloud database transfer

Status: plan only. The ERP and Trench API containers currently target the same PostgreSQL database and role. Native migration history is global (`zebra_schema_migrations`), so schema106 must not be applied there. Deployment namespaces alone do not isolate a schema upgrade.

## Existing authorization and preservation

The user approved implementing the full ERP Agent design, including the necessary isolated ERP services. This bounded transfer preserves every ERP Task/Run/event identifier, existing conversations and native bindings. Trench services, original database, object keys, and unrelated namespaces remain untouched. It is not permission to clone all Trench data or run business operations.

## No-dispatch transfer gate

- Add and test a server-only `admission_paused` maintenance flag. While true, owned chat submit/cancel and mutating client-surface proxy calls reject before Cloud mutation, while authorized history/status reads remain available. Do not rely on a hidden browser button. Drain any request that entered before the flag through existing per-conversation admission locks before stopping services.
- Verify scheduler and other autonomous ERP command/firing producers are disabled; inventory their exact deployed flags and processes. Stop API/Worker before the source snapshot; do not restart a scheduler as part of a readiness test. No shared Trench producer is changed.
- Capture a namespace-scoped baseline ledger of Task/segment status, command queue and idempotency receipts, lease owner/fence/expiry, handoff/effect/dispatch outbox status, and schedule/fire state. Record pending/inflight work without executing, acknowledging, cancelling or deleting it. Unknown queues or independent consumers block cutover until identified.
- Perform row/hash/constraint checks while consumers are stopped. Inspect Worker configuration and invoke only the native read-only schema checker through a plain maintenance entrypoint, with no lease/queue claim. Do not invoke the Worker service or its application bootstrap for readiness; Rabbit disabled does not disable its database consumers or maintenance/model paths. Leave full Worker readiness unclaimed until the step11 release gates pass.
- On API continuity reads, record exact new grant-audit/ledger writes. Before gate release, compare command/outbox/segment/fire ledgers to the source baseline and require no new execution/dispatch.
- Record the explicit first destination metadata mutation and the later first allowed destination dispatch/admission timestamps. Once either occurs, rollback requires the corresponding ledger reconciliation; once dispatch occurs, never blindly copy queues or replay source commands.
- At the accepted cutover, only the destination becomes the ERP consumer. The source ERP API/Worker stay stopped and their original namespace rows remain preserved. Re-enabling a source consumer is a separate reconciled recovery operation.

## Rollback boundary

Before any new canonical writes occur in the dedicated database, restoring the prior ERP-only compose configuration returns to the unchanged source database. After accepted new writes, blind rollback would lose those writes; stop admission and perform an explicit verified forward/reverse namespace reconciliation. Never switch back silently or duplicate business execution. Record the transition point and accepted-write boundary.

## Required runnable checks

The transfer tool needs a dry-run classification/count mode, destination-empty check, exact namespace allowlist, unknown-table refusal, parameterized values/quoted identifiers, no credential logging, failure before destination mutation for a changed scope/schema, source/target hashing, four sequence ownership/next-value checks including empty tables, wrong-namespace rejection, and a disposable database round trip. A successful pg_dump or `/health` does not establish preservation. No public connection details or secrets belong in the evidence document.

## PostgreSQL isolation decision and observed source boundary

The source database grants `CONNECT` to `PUBLIC`. Creating another role on that same server, or revoking a direct grant from that role, cannot subtract its inherited `PUBLIC` permission. Catalog inspection found zero public-schema security-definer functions, but that does not turn the shared server into a separate authentication boundary. Changing the shared `PUBLIC` ACL or authentication rules could affect Trench and is outside this transfer. Therefore the destination uses a separate ERP-only PostgreSQL server, volume and role namespace. No destination container, volume, role or database has been created by this plan.

The actual source is PostgreSQL17.5, image `postgres:17.5-alpine3.21`, config identity `sha256:5d004e058f520673f1f6edbad6b1603d5dab4c818e257c041889ef64672a8cc4`. Reuse this verified local image; the unrelated installed18.3 image is not a compatible same-version transfer target. Live source encoding is UTF8, collation and ctype `en_US.utf8`, locale provider `c`, and the sole extension is `plpgsql`1.0. Reverify the actual source and target server version, encoding, collation/locale provider and collation version immediately before transfer. The source has trusted local Unix-socket access from the existing PostgreSQL container's OS user `postgres`, using database role/database `zebra`; there is no source database role named `postgres`. Native source `pg_dump` can therefore run through `docker exec -u postgres ... pg_dump -U zebra -d zebra` without a password argument. Use the destination container's separately verified local socket path for `psql`, restoring as the dedicated owner role. Neither command line may contain a password or complete DSN.

A read-only native pre-data dump confirms it contains `CREATE SCHEMA public;`. A freshly created destination already has that empty schema. After verifying the exact new destination and absence of all user objects, remove only its empty `public` schema with `DROP SCHEMA public RESTRICT` in the same pre-data restore transaction; never use CASCADE, touch the source schema, or strip native DDL to hide a collision. Any remaining object must abort restoration. This lets native DDL recreate the schema under the dedicated owner.

The subsequent bounded source inspection also identifies35 native public functions and78 non-internal triggers, with zero public SECURITY DEFINER functions. These are part of the native105 schema, not additional table relations. Include their exact names, definitions, security/options, enabled state and deferrability in the approved manifest and verify their native pre/post-data restoration. COPY occurs before destination triggers are restored; never disable source triggers or substitute custom projection/event-position logic. The read-only inspection found the expected138 base tables, one view and four sequences and verified scoped FK closure; its data hashes are preliminary while ERP services remain active, not cutover acceptance.

Before accepting isolation, verify the runtime role is absent on the old server and destination credentials cannot authenticate there. Verify its effective destination attributes and memberships, exact destination volume/image identity, zero published ports and the ERP-only database network membership. API/Worker may retain their existing dependency network and additionally join the ERP database network, but their active DSN must name the unique destination alias and contain only the destination runtime credentials. Remove the maintenance container and its credential files after accepted transfer; preserve protected rollback evidence. ## Smallest transfer tool protocol

Use one Python file with a standard-library host orchestration mode and a lazily imported `psycopg` worker mode. Execute worker mode in a temporary container from the exact pinned105 API image, which already supplies `psycopg`. The Docker host needs no Python package installation. Use existing PostgreSQL containers' native `pg_dump`/`psql`; never invoke native migration application to manufacture the destination schema. A small assert-based check file and an explicitly disposable database round trip are sufficient; no framework, service, queue or transfer registry is needed.

The host uses argument arrays through `subprocess`, protected files/directories (`0600`/`0700`) and a persistent worker subprocess. Secrets enter the worker through a protected read-only mounted configuration file, not command-line arguments or user-facing output. Worker stdin/stdout carries sequential newline-delimited JSON control messages and sanitized metadata only. COPY bytes travel directly between the worker's source and destination `psycopg` connections; they never enter JSON, terminal output or an orchestrator capture buffer. Report phase, counts, catalog/migration digests and row hashes; report failures by bounded phase/SQLSTATE without printing connection strings, SQL parameter values or row contents. The protocol needs only these phases:

1. **`inspect` / `open_snapshot`:** validate exact approved deployment namespaces and definition `(namespace_id, authority_issuer)` pairs, source105 migration ledger/checksums and the complete catalog manifest before destination mutation. Inventory the139 named table/view relations,138 primary keys, all columns/types/order/defaults, generated/identity columns, one view, no partitions, constraints/indexes and four owned sequences. Reject unknown relations, scopes, columns, sequence owners or parameters. Each sequence must have start1, increment1 and no cycle; capture its min/max bounds. Check selected foreign-key closure without widening the allowlist. Begin one source `REPEATABLE READ READ ONLY` transaction, acquire `ACCESS SHARE` locks on the classified base tables to prevent their DDL changing during export, and export its snapshot. Keep this connection and transaction alive until final verification. Emit only the snapshot ID and manifest/count/hash metadata. Revalidate the manifest in that same snapshot.
2. **`dump_schema` / `restore_pre_data`:** while the exported snapshot stays alive, run native source `pg_dump --schema-only --schema=public --no-owner --no-acl` separately for pre-data and post-data, both with that exact `--snapshot`. Keep dumps in protected server files. Before the first restore, verify the destination is the expected distinct server/database/owner and is empty of user objects; revalidate the source against the approved catalog/version/scope fingerprint. Restore pre-data as its dedicated owner with `psql -X -v ON_ERROR_STOP=1 --single-transaction`. Never use source owner credentials or restore ACLs. A lost source snapshot or failed dump stops the transfer; do not silently create another snapshot and combine artifacts.
3. **`copy_rows`:** for each of138 base tables, generate quoted identifiers from the validated manifest and parameterize the exact scope predicates. Copy only approved rows, or the complete unchanged105 migration ledger for its one classified table. Use PostgreSQL text COPY with explicit ordered non-generated columns and bounded streaming buffers; preserve identity-column values explicitly and prove this in the disposable check. Exclude the generated search vector from COPY. Use exact primary-key ordering and a common fixed text-output session configuration (UTF-8, UTC, ISO date style and consistent float/bytea/interval output) on source and target. Record source counts and SHA-256 over a second canonical full-row text COPY stream containing *all* columns, including generated columns, from the same snapshot. Do not hash Python-converted row objects or claim an unordered aggregate is deterministic.
4. **`restore_post_data` / `verify`:** commit copied destination data while consumers remain absent. Restore native post-data with `ON_ERROR_STOP` and a transaction, so primary/unique/foreign-key constraints validate all copied rows. Reject any invalid index or unvalidated expected constraint. For each of the four owned sequences, derive the destination next value from the maximum copied owned-column value; use start1 with `is_called=false` for an empty table, otherwise set a safe next value above the preserved maximum under the inventoried bounds. Check the resulting sequence state arithmetically without consuming `nextval`, and reject exhaustion or unexpected ownership. Recompute every full-row count/hash in exact column/primary-key order, including the regenerated search vector; require equality with the source snapshot. Verify the view DDL, identical105 migration ledger/checksums, exact scope exclusion, preserved Task/Run/event/binding/receipt identities and no command/outbox/fire changes. Only after all checks pass may the source snapshot close and a sanitized verified report be produced.
5. **`abort`:** on any failure, close/roll back the source read-only transaction and any open target COPY transaction; terminate child processes and leave the destination unactivated. Pre-data/data/post-data are separate durable phases, and sequence changes are not transactional rollback evidence. Record the failed destination as incomplete; do not reconnect consumers, erase the source, retry from a fresh snapshot into a nonempty target, or claim that the whole transfer rolled back. Configuration cutover and eventual first dispatch remain separate operator phases under the gates above.

Minimum must-fail checks include changed139/138/1 catalog shape; a missing/changed primary key; an unexpected generated column, partition or view; source schema other than105 or changed migration checksums; a scope value or selected FK dependency outside the exact allowlist; nonempty/wrong destination or privileged/wrong role; source-role presence/authentication by destination credentials; image/version/locale/network drift; missing/unowned/changed/cycling/exhausted sequences; lost exported snapshot; dump/restore/COPY error; generated-column mismatch; any count/full-row hash mismatch; invalid/unvalidated constraints; and unknown or changed execution producers/queue state. Credential redaction and identifier/value separation need negative tests. The disposable round trip must include escaped text/NULLs, JSON, timestamps, preserved identity values, generated-column recomputation, a cyclic FK relationship restored through post-data, empty/nonempty sequences and an injected mid-copy failure. Source writes, source sequence advancement, disabled constraint triggers and replication-role bypass are prohibited throughout.
