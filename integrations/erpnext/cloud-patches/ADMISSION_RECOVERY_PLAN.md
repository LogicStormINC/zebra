# Bounded cold-refresh admission recovery

Status: design only, 2026-10-23. No source/override edits or deployment mutations are included. `resources_impl` retains ownership of the input-admission implementation. This note covers initial Task admission ACK loss and explicit continuation of already admitted input; it does not authorize replaying a model/business Run.

## Existing contracts and failure boundary

Relevant ERP files: `zebra_erpnext/chat.py:_submit`, `cloud.py:request/require_admission_open`, `resources.py:validate_attachments/attachment_digest`, `api.py:snapshot`. Relevant pinned Cloud sources are preserved under `cloud-patches/baseline/` and current compatibility changes under `cloud-patches/overrides/`.

- Initial Task creation is `POST /tasks`, `execute:false`, public key `erpnext-task-<conversation.name>`. Native `app.py:create_session` calls `scoped_idempotency_key`, then `replay_idempotent_response(action='session.create', payload=full_request)` before new admission.
- `session_queue.py` and `postgres/task_admission.py:PostgresTaskAdmissionTransaction` commit the canonical Task/events/binding/input refs and complete idempotency response together. The stored response includes session ID, original preparation sequence, prompt/model/options and ordered attachment refs; no raw attachment body is stored in that response.
- ACK loss can leave an admitted native Task while Host `task_id` is NULL. Browser refresh loses raw selected files. Host currently retains pending text/options/attachment digest and coordinates, not raw files. A digest cannot reconstruct file bytes or the original full POST JSON.
- `chat.py` validates attachment digest before using `prepared_request`; routing a refreshed request through ordinary `_submit(...attachments=[])` therefore cannot safely resume a prepared attached input.
- A maintenance refusal between preparation and command dispatch can leave `task_id` + `prepared_request/prepared_revision` but no pinned `pending_command`. This is a prepared input, not an executed Run and not permission to drop its attachments.

## Existing authorized discovery: useful but incomplete

DEPLOYED 105 `GET /tasks?limit=100` does have exact Host ownership fencing:

`tenant_guard.tenant_scope_response` -> `ApiSessionReadMixin.list_sessions/_authorized_list_response` -> `SessionListApi.list_sessions(authorize_task=...)` -> `_task_principal_response` -> typed `require_task_host_context`.

The verified Grant must retain the original issuer, Host app, namespace, principal, workspace ref and opaque Host thread. Per-candidate Task bindings enforce these; an optional run resource is also checked. Use the original conversation's server-owned coordinates, never a different user/company to widen discovery.

However, `SessionListApi` scans only the deployment's most recent candidate page BEFORE ownership filtering. Limit is at most 100, with no cursor or indexed Host-thread filter. An older matching Task can be absent while the response is empty. Adding an ignored query parameter does not create indexed discovery. Titles/timestamps/one recent matching candidate are not proof of admission identity; multiple successor Tasks may legitimately share a Host thread. Empty results must never trigger another create POST or prove the old POST did not commit.

## Preferred small native read extension: indexed receipt lookup

The existing idempotency store already has direct `(deployment_namespace,action,idempotency_key)` access. Reuse it instead of adding an unbounded Task scan or a new inventory platform.

Proposed fixed route: **GET `/tasks/admission-receipts/<public_key>`**. This is a NEW compatibility read route, not an endpoint already present in deployed 105. Public keys are bounded canonical ASCII identifiers using the needed ERP key alphabet; reject separators, empty/dot segments, percent-encoding ambiguities, duplicate/unknown query parameters, and overlength keys. Action is fixed to `session.create`; callers cannot request arbitrary idempotency actions or storage keys. No request body or attachment bytes are required.

### Authorization placement

1. In `apps/api/src/zebra_agent_api/http_host_auth.py:validate_host_target`, recognize this exact route before the ordinary `/tasks/<uuid>` branch attempts UUID parsing. Existing Host middleware already treats `/tasks/` as requiring target validation before Grant consumption; retain that ordering, deadline and fresh single-use JTI behavior.
2. Derive the storage key with `zebra_agent_api.idempotency.scoped_idempotency_key(public_key, verified.context)`. Its authority partition includes Host app, namespace, principal and workspace, but NOT issuer, Host thread or run. Consequently a key hit alone is insufficient authorization.
3. Read `app.stores.idempotency.get(action='session.create',idempotency_key=derived_key)`. Missing -> typed 404 `admission_receipt_not_found`. Incomplete/empty/invalid response -> explicit reconciliation error, not a successful empty Task.
4. Extract the native root Task UUID from the committed response's `session_id`/`task_id`, requiring both to agree if both exist. Resolve `original_create_run_id` through a fixed internal indexed read of `task_binding_snapshots` constrained by `deployment_namespace`, this root `task_id`, and `binding_revision=1`; select `task_id,binding_revision,binding_digest,snapshot_json`. Initial `bind_task` freezes revision1, while `save_task_binding` appends later renewals. Do not use `load_task_binding` for this original association: it orders revisions DESC.
   Validate `snapshot_json` as `TaskBindingSnapshot`, require both row/model Task IDs equal the receipt's root Task, require row/model revision both1, and explicitly compare the model's computed `binding_digest` to the **stored row's** `binding_digest`. Existing `task_admission._binding_from_snapshot` compares computed digest with computed digest through `_binding_digest_of`; that check alone does not authenticate the stored digest column. Require an original Host context and `host_context_digest(original_context)==initial_binding.host_capability.grant_digest`, then exactly one nonempty original run resource. Retain and verify the original issuer/Host/namespace/principal/thread/workspace link when authorizing the receipt; require latest binding and caller to preserve that original identity. An additional immutable native create-intent association, if introduced, must bind this same receipt/hash/Task and agree with revision1 rather than replace missing revision1. The Host's saved original admission run, if present, must agree too. Never derive the expected run from the browser, caller's current Grant, latest binding, active segment, latest Run or a successor Task. Missing revision1, corrupt stored digest/context digest, no run, multiple run refs, or disagreement yields `admission_receipt_reconciliation_required`, with zero receipt metadata disclosure, coordinate adoption or POST.
   Then load and validate the latest typed Task binding and call `require_task_host_context(binding,verified.context,task_id=...,run_id=original_create_run_id,now=...,authority_issuer=verified.authority_issuer)` with the original run explicitly supplied. Keep exact principal/thread/workspace/issuer checks; do not accept a namespace-only match. The original admission Grant may now be expired: its immutable context supplies historical identity only, never fresh execution authority. The currently verified Grant must be unexpired and otherwise authorized. `run_id=None` is insufficient: the native helper otherwise accepts an arbitrary single caller run ref. Apply the same original-run resolution and explicit check in both pre-consumption target validation and the authorized read; neither phase may substitute the caller's run for the immutable expected run.
5. Only after target authorization may the read adapter in `task_routes.py` return the receipt. Keep preflight and read under the native bounded I/O discipline and recheck identity/expiry before return; do not turn a time-of-check race into disclosure. Prefer an immutable prepared read result passed internally, or repeat the O(1) read/binding check rather than caching authority outside the request.
6. Do NOT call `app.create_session`, `reconcile_replayed_run`, any POST replay path, projection repair, Worker dispatch or object staging from this GET. `session_replay.py:reconcile_replayed_run` can submit a run for `execute:true`; it is expressly inappropriate for this read operation.

Implement stored-binding validation once in the existing shared native binding reader, after inventorying every `_binding_from_snapshot`/`_read_task_binding` caller. Extend its row projection and shared validation to compare stored Task/revision/digest with the typed snapshot; preserve valid latest/session-binding callers and reject corrupt rows consistently. Reuse that validation for the small fixed revision1 read, rather than add a second bespoke digest validator only for receipts. Keep original-admission lookup an internal fixed-revision operation; do not add a public arbitrary-revision selector or change persisted digest/hash semantics. Add a corrupt-row regression through both ordinary latest-binding reads and receipt lookup.

Proposed response schema, version 1:

```
{contract_version:1, action:'session.create', public_key:<requested key>,
 original_create_run_id:<immutable original run>,
 request_hash:<native stored 64hex>, receipt_status_code:201,
 receipt:<original committed metadata response>}
```

The Host consumes this server-to-server result and stores only its needed metadata. Browser recovery state should not expose internal storage keys, private configuration or raw file bodies. Original receipt sequence is an admission coordinate; get a separate authorized current header before deciding whether a new command can be constructed. Do not overwrite a pinned command's revision with a newer header.

Historical genuinely runless creates require a separate explicit compatibility decision. A metadata-only read may be supported only when immutable original admission evidence positively proves zero run refs and the freshly verified current context also has exactly zero run refs, together with all exact Task ownership checks. Absence of historical evidence is not proof of a runless create. Such a response must explicitly mark `runless_historical`, cannot authorize execution or invent a create run, and is **not eligible for ERP cold-refresh adoption or prepared-input resume**. The ERP recovery operation denies this compatibility case with reconciliation required. A historical record with an unresolved or ambiguous run is denied even metadata-only access through this route.

If indexed Host-thread discovery is later needed for a general inventory, derive filters from the verified Grant and query canonical bindings by exact issuer/Host/namespace/principal/workspace/thread with bounded pagination and suitable indexing; authorize each returned latest binding. That is a separate route/storage improvement. Receipt lookup is smaller and avoids the recent-100 limitation for this known-key recovery problem.

## Canonical hash, metadata and Host schema

Native full-request hash is exactly `zebra_agent_api.idempotency.request_hash(payload)`: SHA-256 over `json.dumps(payload,sort_keys=True,separators=(',',':')).encode('utf-8')` with Python's default `ensure_ascii=True`. Hash the actual complete wire request before its FIRST HTTP attempt, including normalized base64 attachments, execute:false, workspace source, prompt/title, model/effort and all explicit preset fields. Do not substitute the attachment digest, a Pydantic model dump with defaults, or JSON using `ensure_ascii=False`.

Proposed additive internal Host fields (no ordinary DocType write permissions):

- `admission_public_key` (bounded Data) and `admission_request_hash` (64hex Data), committed BEFORE the initial HTTP attempt; original request UUID/run/options remain immutable. Retain the Host's original create-run coordinate for comparison, but native authorization must independently derive its expected run from immutable Cloud admission evidence. On recovery require exact agreement; a Host field cannot override Cloud's association.
- `prepared_input_json` (Long Text containing metadata only): contract version, action/public key, Task/segment/preparation sequence, canonical message-event association where available, model/options, ordered native attachment refs and their original-byte digest, plus the verified receipt request hash.
- Optional bounded `recovery_state` (`not_sent`, `unknown`, `admitted`, `command_pinned`, `accepted`, `blocked`) and visible reason. These describe evidence; do not mark a timeout as definitely not sent.

Use the existing `install.setup` additive missing-field pattern. Do not backfill a guessed wire hash or rewrite old Task bindings. Persist metadata atomically with Task/prepared coordinates after successful original ACK or validated recovery. Record intent/hash before any operation that can commit a Grant and contact Cloud.

`resources.attachment_digest` is a DIFFERENT algorithm: SHA-256 of ordered `{file_name,media_type,sha256(original bytes)}` coordinates serialized with ensure_ascii=False. It proves ordered file identity, not complete request meaning. Native refs for extracted documents use `original_media_type` and `original_sha256` for this comparison; their regular media_type/sha256 describe extracted text. Text/image refs use their normal media_type/sha256. Preserve count, ordering, names and types. Do not hash extracted text as if it were the original PDF/DOCX/XLSX/PPTX. Reject missing/ambiguous provenance; retain the original digest without normalizing away changed intent.

Compatibility: new requests require the saved full wire hash to equal the native receipt hash before adopting coordinates. For existing pending records lacking that hash, do not fabricate one. A narrowly versioned reconciliation may compare original receipt prompt/model/options plus the exact ordered original-byte attachment digest to the already stored Host metadata, after exact binding authorization. If any required association or metadata is unavailable or ambiguous, expose `reconciliation_required`; request original files for an explicit identical retry or operator diagnosis. Never choose a Task by title/time, claim a byte digest proves arbitrary missing options, or POST a smaller request under the original key.

404 only means no COMMITTED receipt was visible at that read boundary. The original HTTP admission could still be in flight. Continue read-only reconciliation or explicit diagnosis; do not switch request IDs, delete staged objects, or infer absence of business effects from it. Exact same-body replay is permitted only when all original bytes/options remain available and the user explicitly requests recovery, under the same key; never reconstruct absent file bytes from hashes.

## Host explicit recovery and prepared-input resume

Add fixed owned BFF operations, for example `recover_admission(conversation)` (read/reconcile only) and `resume_prepared(conversation)` (explicit dispatch). Browser supplies no Cloud path, Task ID, raw replacement attachments, principal, workspace or idempotency key.

### `recover_admission`

- Require current enabled user, conversation ownership, current company read permission and the existing per-conversation admission lock. Use original Host thread/workspace; preserve legacy/private generation.
- While maintenance is paused, allow this bounded GET reconciliation and Host metadata repair, but no POST/create/append/model/command. Issue the current single-use Grant for the server-owned original create run. Recover the committed receipt through the fixed native GET, verify its independently resolved original-run association against the immutable Host intent, verify full hash or the explicit compatibility proof above, then atomically restore `task_id`, `prepared_request/prepared_revision` and verified input metadata. Missing/ambiguous/runless original-run evidence blocks ERP adoption; do not dispatch automatically on page refresh.
- If `pending_command` already exists, report that exact durable command as awaiting explicit retry/observation. Do not rebuild it from browser files, preferences or current page.

### `resume_prepared`

- Require explicit user action, current ownership/company and private capability authorization, then serialize with submit/cancel using the same lock. Maintenance must be open immediately before each prospective non-GET; gate failure retains all intent, metadata, pinned commands and original keys. A maintenance check is an admission linearization boundary, not a claim to undo a request already sent.
- If `pending_command` exists, validate its saved identity/input binding and replay the byte-identical semantic JSON envelope with its SAME `erpnext-run-<request_uuid>` key, or observe canonical accepted/finished state. Do not rewrite expectedRevision, run ID, inputs, extensions or UI state. No create/append/attachment admission occurs.
- If native input is proven admitted and there is NO pinned command, use stored pending_message and immutable request_options/prepared input refs. Recheck the native exact receipt/event association, original-byte attachment digest and Task binding, and read current header/canonical run metadata to establish whether this prepared input has already been consumed. Do not use the ordinary submit validation path with an empty attachment list. Never append the same human message again merely because task_id exists.
- An unconsumed prepared input can construct its first command using its native preparation revision, original run/options and canonical admitted refs; AG-UI contains no raw files. If native revision/turn has advanced incompatibly, report a conflict/reconciliation state instead of rebasing the input or replaying another turn. If original run is already accepted/terminal, observe it; do not execute again.
- Page-bound surface handling is a separate controlled prerequisite. A saved full surface for the same run can be reused only when it remains valid for its intended page/session/revision; stale navigation/form handlers must stay unavailable until an explicit supported remount/reconnect. A fresh current page may be used when building the FIRST unpinned command only after explicit user action and normal profile/controller fences. Once the command is pinned, page changes cannot justify rewriting it.
- Retain the existing opening_run/opening_at unknown-ACK marker and 420-second lease/transport window. Never reopen another controller while first surface creation is uncertain. Known expired/fenced sessions follow native explicit cleanup rules. Do not auto-run files/business actions after a reconnect.
- Persist a newly constructed command BEFORE the HTTP attempt. If maintenance activates after preparation/pinning but before HTTP, leave it pinned and surface an explicit paused state. If command ACK is lost, exact replay/observation is the only next step. Existing stop-command pinning and business confirmation identity remain unchanged.

## Required smallest runnable checks

### Extension: recover the current followup or clarification input

The initial-create lookup above does **not** cover every unknown admission. `chat.py:_submit` persists the new request UUID, `pending_message`, options and byte digest, then sends `POST /tasks/{root}/messages` with `erpnext-message-v2-<request_uuid>`. It saves the new `prepared_request/prepared_revision` only after the response. A lost append ACK therefore leaves a known Task but the PREVIOUS prepared UUID; after refresh the new file bytes are gone. Replaying the original `session.create` receipt proves only the old input. It must never mark this newer message prepared or justify appending it again.

Reuse the native `http-input:{rootTaskId}` receipt created by `postgres/http_input_messages.py:claim_input_receipt/materialize_http_input`. Add one fixed owned read route **GET `/tasks/{rootTaskId}/input-admission-receipts/{public_key}`**, with the same strict key/path/query parsing and bounded Host pre-consumption validation as the initial route. Internally action is server-derived `http-input:<validated root UUID>`; the storage key uses the verified context and `scoped_idempotency_key`. Do not accept an action, storage key, Segment, Run or event selector from the browser. One direct idempotency read plus fixed indexed Task/binding/event reads suffices; no Task listing, append POST, object read or model replay is necessary.

#### Immutable native input-receipt association

The current full response includes root/Segment/sequence/content/refs but not a complete original-input authority or event identity. A text-only input has **zero attachment metadata rows**, so attachment proof cannot supply its original input Run. Before enabling this GET, atomically add a versioned server-owned `input_admission` JSON member to the existing complete idempotency response in `materialize_http_input`, for every input, including text-only and clarification. This uses existing JSON storage rather than a new table or guessed attachment join. It is part of the committed replay receipt, not an after-commit save. Preserve existing response keys, status, original wire request hash, event ordering and replay identity. Its typed contents are:

```
{contract_version:1, action:'http-input:<root UUID>', request_hash:<stored wire hash>,
 task_id:<root>, segment_id:<canonical event Session>, event_id:<canonical UUID>,
 event_type:<'user_message_received'|'clarification_responded'>,
 segment_sequence:<canonical sequence>, task_sequence:<allocated native coordinate>,
 clarification_id:<canonical ID or null>,
 run_binding:<required tagged {kind:'none'} | {kind:'single',run_id:<exact admitted run>}>,
 event_created_at:<canonical event timestamp>, authority:<typed HttpInputAuthority>,
 input_context_digest:<host_context_digest of the verified input context>,
 binding_revision:<immutable input-time Task binding revision>}
```

Construct `authority` only from the verified consumed Host evidence already used by this admission; its binding digest must equal the exact immutable input-time binding row's stored/typed digest. Preserve existing shared native admission semantics: zero run resources is valid and MUST persist the explicit required `run_binding={kind:'none'}` without rejecting an otherwise valid generic Cloud input. Exactly one run resource records `{kind:'single',run_id:...}` from THAT consumed input context. Multiple run resources remain native-invalid; missing/malformed association is not equivalent to the explicit `none` variant. **Exactly one Run is an ERP recovery eligibility requirement, not a new shared admission requirement.** The input-time binding's own Host context may describe a previous Run; it cannot replace the consumed input context's Run. Store the association even when `PreparedHttpInputBatch.entries` is empty. It contains no JWT, credential, raw bytes, data URLs or browser-supplied authority. Treat the authority association as server-to-server receipt metadata; the BFF keeps it in internal fields and exposes only necessary recovery status/coordinates to the browser. If the native public POST DTO must remain byte-for-byte unchanged, use a shared receipt serializer to omit this JSON member from ordinary POST/replay responses, while retaining it internally; do not write a second authoritative receipt.

At read, validate the typed member against the fixed action/root/stored request hash, complete original receipt body, immutable input-time binding row, and canonical event. Use the shared stored-row Task/revision/digest validator described above, with this internally recorded revision (never a public arbitrary-revision parameter). Compare the stored `input_context_digest` to `host_context_digest(authority.context)` and verify the consumed proof's original accepted audit/ledger association, including issuer/JTI/grant digest and context scopes/resource digests (the latter binds the input Run). This is a bounded historical association check: do not call the ordinary fresh admission check on an expired original Grant or demand that historical registry policy still be current. Missing retained evidence fails closed for reconciliation. Validate exact issuer/Host/namespace/principal/thread/workspace linkage; canonical `event_id`, type, Session/Segment, timestamp, sequence, Task membership and allocated `task_sequence` must agree. For clarification require the same canonical clarification ID. Attachment refs, including an empty list, must agree with that exact event; do not infer the event from latest user text or a matching title. The original consumed evidence is historical admission evidence and may now be expired; it is not current execution authority.

For the eligible `single` variant, authorize the GET using a freshly verified current unexpired Grant against the LATEST typed Task binding, explicitly passing `run_id=input_admission.run_binding.run_id` and `authority_issuer=verified.authority_issuer` to `require_task_host_context`. Also preserve the immutable original Task identity/thread/workspace/issuer linkage. A fresh Grant for a later/current Run does not authorize reading this receipt merely because the root Task matches. Read/recheck the same association in pre-consumption validation and the final adapter; no `run_id=None` shortcut for this variant. The explicit `none` variant is valid native admission evidence but **ERP-recovery-ineligible**: ERP lookup/adoption/resume returns reconciliation required and makes zero POSTs, without fabricating a Run or changing the original admission result. Any separately supported generic metadata-only read of `none` requires an exactly runless fresh current context plus all Task ownership checks, just like the historical runless create compatibility policy; it cannot enable ERP resume. The initial-create GET retains its separate **revision1 original-create Run** rule; never use revision1's create Run as every followup's expected Run.

Return a versioned action/root/public-key/hash/receipt envelope analogous to initial recovery. The native stored receipt hash must equal the Host's saved full wire hash before adoption. Missing receipt remains unknown at that read boundary; missing/corrupt association, wrong Run/authority/event/Task membership or a pre-extension receipt without sufficient immutable association yields `admission_receipt_reconciliation_required`. Do not backfill a followup Run from latest binding, attachment rows, current Grant or Host preferences. For historical followups lacking the association, this GET fails closed even if four file rows happen to exist; recovery requires separate explicit diagnosis or an identical same-key retry only when all original bytes/options still exist. Never POST an empty/smaller body under the old key.

#### Host intent and explicit resume

Add a bounded internal `pending_admission_json` (or extend the already proposed internal intent JSON) alongside, rather than overwriting, immutable initial-create fields. Before EACH prospective create/append HTTP attempt, commit `{contract_version, kind:create|followup|clarification, request_uuid, public_key, root_task_id|null, input_run_id, full_wire_request_hash, original_attachment_digest, clarification_id|null}` using the actual final wire body, including whether `attachments` was absent or present and the exact clarification ID. These fields describe the input request, not the later AG-UI command. Preserve the prior prepared UUID until the current receipt is proven; never equate a known Task ID with successful current input admission. New immutable intent cannot replace an older unknown intent.

`recover_admission(conversation)` selects only the fixed create or input receipt GET from this server-owned intent; browser supplies no action/key/Task/Run. After current enabled-user/owner/company checks and the existing lock, verify native full wire hash, original-byte attachment identity, original input Run and exact canonical event association. Atomically restore the CURRENT `prepared_request/prepared_revision` and metadata, without create/append/AG-UI/model POST on refresh. An unknown ACK may have completed terminal rollover and native dispatch: inspect the canonical input Turn/Run first, and report/observe accepted work; do not manufacture another command. A clarification may also have become runnable through native continuation; check its exact event and native continuation/command state before explicit resume.

`resume_prepared` retains all earlier maintenance, surface/page fencing and pinned-command requirements, now against the specific recovered current input event. With a pinned AG-UI envelope, preserve its exact original key/revision/body. Without one, prove this exact input has not already been consumed or dispatched through native Turn/Run/continuation state before constructing its first command; absence of a Host `pending_command` is not that proof. In particular, never turn a recovered terminal rollover outbox or clarification continuation into a duplicate run. If native evidence cannot establish the next permissible command, report reconciliation and make no POST.

Required extension checks: cold-refresh lost ACK for active followup, terminal rollover and clarification, each with FOUR files and with TEXT ONLY; lookup must recover the new input rather than the older create/prepared receipt, and refresh makes zero POSTs. Include committed rollover/continuation dispatch and require observation without duplicate command, append, outbox or model. Check current input Run differs from create and later renewed binding Runs: only a fresh Grant for the immutable admitted input Run succeeds. Preserve the actual generic runless fixture (`f.authority` has principal/thread and no Run): otherwise valid native text/file/clarification admissions still commit successfully with explicit `run_binding.kind='none'`; ERP recovery/adoption/resume rejects that same valid receipt as ineligible with zero POSTs, no guessed/backfilled Run and no mutation of native admission. Verify `single` records the exact consumed Run, multiple Runs remain rejected, and absent association cannot be treated as `none`. Reject wrong principal/company/issuer/thread/root/event/clarification/hash, malformed or absent receipt authority, zero-file receipts lacking authority, and historical guessed associations, with zero adoption/POST. Exercise maintenance before append, after append commit/before ACK, after recovery/before command pinning, and unknown exact AG-UI ACK; retain all original keys/digests and never reconstruct missing file bytes.

This extension is design only. It does not change the currently frozen followup overrides, schema, manifest, deployment or acceptance claim.

1. Initial admission with FOUR mixed supported files commits then loses ACK; discard browser raw payload and reconstruct a new process/session from Host DB fields only. GET recovery returns the exact native Task/refs/hash; no create/append/command POST is made during refresh/reconciliation. Explicit resume dispatches only the first run under its original key. Original attachment bytes are never stored in Host control fields.

5. Already known Task + prepared_request + four admitted files + no command: explicit resume verifies metadata, uses original preparation revision, creates one command, and makes zero input append/create calls. 6. Simulate maintenance before initial HTTP, after Task ACK, after input ACK, after command pinning and immediately before HTTP. 8. Changed page, stale UI revision, expired same-run surface and unknown opening ACK: no unguarded remount/second active controller and no page action until native fences permit it. No reconstruction of a pinned command to substitute new UI coordinates.
